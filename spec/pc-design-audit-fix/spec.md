# Feature Specification: Weavr PC 端 HarmonyOS Design 审查整改

**Created**: 2026-07-24
**Status**: Draft
**Input**: 对 Weavr 项目 PC 端三分栏布局进行 HarmonyOS Design 合规审查，修复发现的 10 项设计问题（5 MAJOR + 5 MINOR），确保输入反馈完整性、窗口架构合理性、主题适配性和无障碍可用性。

## Overview

Weavr 的 PC 端三分栏布局（侧栏 → 文稿列表 → 编辑区）已具备核心功能，但经过 HarmonyOS Design 严格审视后，发现以下缺口：所有按钮缺少瞬时按压反馈、鼠标悬停态未实现、键盘焦点链不可用、系统标题栏和自定义顶栏形成"双层帽"浪费纵向空间、无深色模式支持、色彩 Token 命名失实且存在两套并行的色彩体系、折叠导航栏无选中指示、图标按钮无读屏语义标签。

本次整改目标：在不改变现有三分栏架构和核心交互的前提下，为 PC/2in1 用户补全完整的输入反馈体验（触摸、鼠标、键盘），重构窗口标题栏融合方案以释放写作空间，建立统一的深色/浅色双模式色彩 Token 体系，并为所有交互元素添加无障碍标签。

## User Scenarios & Testing

### User Story 1 — 完整的 PC 输入反馈体验 (Priority: P1)

作为 PC/2in1 用户，我点击侧栏、工具栏、文稿列表中的任何按钮时，按钮立刻产生视觉变化（变色/缩放），让我知道系统已接收到我的操作。当我用鼠标划过可交互区域时，元素出现悬停高亮效果。当我用键盘 Tab 键在侧栏、文稿列表、编辑区工具栏之间跳转时，焦点态清晰可见且顺序合理。

**Why this priority**: 输入反馈是交互设计的基础——没有反馈的 UI 让用户怀疑操作是否生效。PC/2in1 设备的核心输入方式（鼠标悬停、键盘 Tab）目前完全缺失，属于发布前必修复项。

**Independent Test**: 在 2in1 设备上运行 Weavr，用鼠标点击任意按钮、划过任意列表项、按 Tab 键遍历界面——每个操作都有即时视觉反馈。可独立于窗口标题栏、深色模式等后续需求验证。

**Acceptance Scenarios**:

1. **Given** PC 布局已加载, **When** 用户用鼠标或手指按下"新建文稿"、"H1"/"B"/"I"工具栏按钮、侧栏库列表项, **Then** 按钮在按下瞬间（< 50ms）出现背景色加深或缩放变化，抬起后恢复
2. **Given** PC 布局已加载且用户使用鼠标, **When** 光标划过侧栏列表项、文稿卡片、工具栏按钮、"写作伴侣"快捷按钮, **Then** 元素出现柔和背景色变化（100ms 过渡），光标移出后恢复
3. **Given** PC 布局已加载且用户按 Tab 键, **When** 连续按 Tab, **Then** 焦点按侧栏 → 文稿列表 → 编辑区 TabBar → 工具栏 → 写作伴侣面板的顺序移动，当前焦点元素有明显的蓝色边框指示
4. **Given** 按钮处于按下态, **When** 用户将手指/光标移出按钮区域, **Then** 按钮视觉反馈消失，操作被取消

---

### User Story 2 — 标题栏融合与纵向空间解放 (Priority: P1)

作为 PC/2in1 用户，我打开 Weavr 后看到的是一个统一的标题栏（包含应用名称和窗口控制按钮），而不是"系统标题栏 + 自定义顶栏"的双层结构。编辑区因此获得了约 80vp 的额外纵向空间，能在同一屏内多看几行文字。

**Why this priority**: 写作应用的核心价值是"多看几行字"。当前双栏结构浪费 80-100vp 的宝贵垂直空间，且系统标题栏的默认样式与 Weavr 的蓝色 UI 不协调。这是架构级改进。

**Independent Test**: 在 2in1 设备上启动 Weavr（窗口 ≥ 840vp 宽度），验证：(a) 窗口中无系统原生标题栏，(b) 应用顶部有自定义标题栏显示 "Weaver 鸿蒙全场景小说创作平台"，(c) 在标题栏空白区域拖拽可移动窗口，(d) 编辑区高度比改进前增加约 80vp。可独立验证，不依赖输入反馈改进。

**Acceptance Scenarios**:

1. **Given** 应用在 PC（≥ 840vp）窗口模式下启动, **When** 窗口显示, **Then** 系统原生标题栏不可见，应用顶部为统一的自定义标题栏
2. **Given** 自定义标题栏已显示, **When** 用户在标题栏空白区域按下并拖拽, **Then** 窗口跟随鼠标移动
3. **Given** 自定义标题栏已显示, **When** 用户将窗口缩小至 < 840vp, **Then** 系统恢复默认标题栏，布局切换为手机/平板模式
4. **Given** 侧栏或编辑区获取焦点, **When** 用户在此区域按下并拖拽, **Then** 不触发窗口移动；仅在标题栏空白区域拖拽时才移动窗口

---

### User Story 3 — 深色模式支持 (Priority: P2)

作为 PC/2in1 用户，当系统切换到深色模式时，Weavr 的整个 PC 布局（侧栏背景、文稿列表、编辑区、工具栏、写作伴侣面板）自动切换为深色配色方案，文字色从深色变为浅色，强调蓝 #007DFF 保持品牌识别，编辑区背景从 #F5F5F5 切换为舒适的深色。

**Why this priority**: 深色模式是 HarmonyOS 平台的基本要求，也是写作用户在夜间/暗光环境中的刚需。当前 PC 布局完全不支持深色模式，浅色 UI 在暗光下刺眼。

**Independent Test**: 在 2in1 设备上切换系统深色模式，Weavr PC 布局自动切换为深色主题；切回浅色模式后恢复浅色主题。可独立验证，不依赖输入反馈或标题栏改进。

**Acceptance Scenarios**:

1. **Given** 系统设为浅色模式且 Weavr PC 布局已显示, **When** 用户切换到系统深色模式, **Then** 整个 PC 布局（侧栏、文稿列表、编辑区、工具栏、状态栏、写作伴侣面板、自定义标题栏）在 300ms 内平滑过渡到深色配色
2. **Given** 系统深色模式下 Weavr 已显示, **When** 用户查看编辑区, **Then** 文字色为浅色，背景色为深色，对比度满足可读性要求
3. **Given** 系统深色模式下, **When** 用户选中文库项或项目, **Then** 强调蓝 #007DFF 作为选中色保持一致，仅背景和文字色切换

---

### User Story 4 — 无障碍与色彩体系一致性 (Priority: P3)

作为依赖屏幕朗读器的用户，我使用读屏软件浏览 Weavr PC 布局时，能听到每个按钮的正确功能描述（如"显示侧边栏"、"新建文稿"、"收起文稿列表"），而非无意义的"等号"、"叉号"。同时，应用的色彩 Token 命名清晰且历史遗留的 GREEN Token（实为蓝色）已被清理，手机端和 PC 端使用统一的蓝色强调色系。

**Why this priority**: 无障碍是 HarmonyOS 平台的基本要求，对依赖辅助工具的用户至关重要。色彩 Token 一致性影响长期维护效率和品牌统一性。这些改进不影响核心交互流程。

**Independent Test**: (a) 打开屏幕朗读器，Tab 遍历 Weavr PC 布局的所有按钮——每个按钮播报正确的功能描述。(b) 代码中不再存在命名为 GREEN 但实际值为蓝色的 Token。可独立验证。

**Acceptance Scenarios**:

1. **Given** 屏幕朗读器已开启, **When** 焦点移至侧栏的 `≡`、`★`、`✦` 图标按钮, **Then** 朗读器分别播报"显示侧边栏"、"收藏"、"灵感池"
2. **Given** 屏幕朗读器已开启, **When** 焦点移至编辑区工具栏的全屏按钮、Tab 关闭按钮, **Then** 朗读器分别播报"全屏模式"、"关闭标签页"
3. **Given** 开发者查看 `PcDesignTokens.ets` 源码, **When** 搜索 `GREEN` / `GREEN_DEEP` / `GREEN_SOFT` / `LINE_2` / `INFO` 旧 Token 名称, **Then** 这些名称已不存在，全部替换为语义正确的命名
4. **Given** 手机/平板 Tabs 布局中选中态的 Tab 标签, **When** 开发者查看 Index.ets, **Then** 选中色引用统一的蓝色强调 Token，而非旧的绿色色值

---

### User Story 5 — 视觉精致度抛光 (Priority: P3)

作为 PC/2in1 用户，在侧栏折叠为 56vp 导轨时，我能看到当前激活的文库项有一个蓝色小圆点指示器。打开查找替换栏时，面板从顶部平滑滑入而非突然出现。侧栏的折叠按钮在正常布局流中跟随标题行，不会因窗口尺寸变化而错位。

**Why this priority**: 这些是细节抛光项，不影响核心任务完成，但显著提升整体体验的精致感和专业感。

**Independent Test**: (a) 折叠侧栏后观察 Rail 图标上的激活指示器。(b) 触发查找栏，观察出现/消失动画。(c) 调整窗口宽度，观察折叠按钮位置是否稳定。可独立验证。

**Acceptance Scenarios**:

1. **Given** 侧栏折叠为 56vp Rail 且"全部文稿"为当前激活库, **When** 用户查看 Rail 上的 `≡` 图标, **Then** 图标下方可见蓝色圆点指示当前激活态
2. **Given** 编辑区显示文稿内容, **When** 用户点击查找按钮触发查找栏, **Then** 查找栏从编辑区顶部平滑滑入（200ms 标准曲线），编辑区内容同步下移
3. **Given** PC 布局已显示, **When** 用户调整窗口宽度从 840vp 到 1200vp, **Then** 侧栏折叠按钮始终位于标题行右侧，不与下方内容重叠

---

### Edge Cases

- **超窄 PC 窗口**: 用户将窗口从 1200vp 拖窄至刚好 840vp（PC 布局阈值）时，所有按钮按压/悬停/焦点反馈仍正常工作，标题栏融合保持有效
- **深色模式下按钮按压**: 深色模式中按下按钮时，背景色变化方向正确（浅色按钮变深、深色按钮变浅），而非统一加深导致不可见
- **键盘焦点在隐藏面板中**: 当写作伴侣面板或查找栏关闭时，焦点不滞留在已隐藏元素上，自动回退到编辑区
- **标题栏拖拽与内容区交互冲突**: 用户点击标题栏中的文本或 Logo 时不应触发窗口移动，仅在标题栏空白区域拖拽时移动
- **从深色模式启动应用**: 用户设置系统为深色模式后再启动 Weavr，PC 布局直接以深色主题渲染，无闪烁
- **折叠 Rail 所有项折叠**: 当所有面板都折叠时，Rail 仍然可见且可操作，用户仍可展开面板

## Requirements

### Functional Requirements

- **FR-001**: 系统必须为 PC 布局中所有可交互 Button 组件提供瞬时按压视觉反馈（< 50ms）
- **FR-002**: 系统必须为 PC 布局中所有可交互元素提供鼠标悬停视觉反馈（100ms 过渡）
- **FR-003**: 系统必须支持 Tab 键在侧栏 → 文稿列表 → 编辑区 → 写作伴侣面板之间按合理顺序移动焦点，焦点元素有清晰的蓝色边框指示
- **FR-004**: 在窗口宽度 ≥ 840vp 时，系统必须隐藏系统原生窗口标题栏，显示自定义标题栏
- **FR-005**: 自定义标题栏必须支持窗口拖拽移动功能，仅在标题栏空白区域触发
- **FR-006**: 系统必须响应系统深色/浅色模式切换，在 300ms 内平滑过渡整个 PC 布局的配色
- **FR-007**: 深色模式下编辑区文字与背景的对比度必须满足可读性要求
- **FR-008**: 系统必须为所有仅使用 Unicode 图标的按钮提供 `accessibilityText` 语义描述
- **FR-009**: 系统必须消除 PcDesignTokens 中以 GREEN 命名但实际为蓝色值的 Token，全部替换为语义正确的命名
- **FR-010**: 手机/平板 Tabs 布局与 PC 布局必须使用统一的蓝色强调色体系
- **FR-011**: 侧栏折叠为 56vp Rail 时，激活态的文库项必须显示可见指示器
- **FR-012**: 查找替换栏的出现与消失必须使用平滑的组合过渡动画（平移 + 透明度）
- **FR-013**: 侧栏折叠按钮必须使用标准 Flex 布局定位，不得使用绝对坐标 `position()` hack

### Key Entities

- **交互状态**: 每个可交互元素维护四种状态 — normal（默认）、pressed（按下）、hovered（悬停）、focused（焦点）。状态间过渡时间遵循官方参考值：按压即时、hover 约 100ms、焦点即时。
- **色彩模式**: 双模式 Token 体系，每色值包含浅色模式值和深色模式值。由系统色彩模式驱动的全局切换，组件渲染时根据当前模式选择对应色值。
- **窗口装饰**: 窗口标题栏的显隐状态。宽度 ≥ 840vp 时隐藏系统装饰并启用自定义标题栏；宽度 < 840vp 时恢复系统默认。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 100% 的 PC 布局可交互 Button 在按下时产生可见反馈
- **SC-002**: 100% 的 PC 布局可交互元素在鼠标悬停时产生可见反馈
- **SC-003**: Tab 键可在 5 次按键内从侧栏遍历至编辑区工具栏
- **SC-004**: 标题栏融合后编辑区可见行数增加 ≥ 3 行（以默认 16fp 字号计）
- **SC-005**: 深色模式切换过渡动画完成时间 ≤ 300ms，无闪烁或色块跳跃
- **SC-006**: 深色模式下编辑区文字对比度 ≥ 4.5:1（WCAG AA 标准）
- **SC-007**: 屏幕朗读器播报所有图标按钮的语义描述，零个"无标签"播报
- **SC-008**: 代码中无任何命名为 GREEN 但实际值为 #007DFF 系列的 Token
- **SC-009**: 手机端 Tabs 选中态和 PC 端选中态使用同一蓝色色值

## Assumptions

- 目标 HarmonyOS API Level 22 (6.0.2)，`setWindowDecorVisible()` / `stateStyles` / `onHover()` / `focusable()` / `accessibilityText()` / `ConfigurationConstant.ColorMode` 等 API 在当前 API Level 均可用（已通过知识库验证）
- 2in1/PC 设备上 `setWindowDecorVisible(false)` 生效且不影响其他窗口管理功能
- 系统深色模式切换通过 UIAbility 的 `onConfigurationUpdate` 回调通知，应用通过 AppStorage 传播状态
- 现有 `breakPoint` 机制保留，标题栏融合仅在 `BreakPoint.LG`（≥ 840vp）时生效
- 当前的 Unicode 图标（≡ ★ ✦ 等）暂不替换为 SVG 资源，仅添加无障碍语义标签；图标资源替换属于后续视觉优化任务，不在本轮范围
- 现有深色模式资源目录 `resources/dark/` 已存在，仅需补充 PC 布局的色值定义
- 手机/平板端（SM/MD 断点）的输入反馈改进不在本轮范围，本轮仅覆盖 PC 布局
- 打字机/聚焦/沉浸三种写作模式、写作伴侣后端对接、关系图 Canvas 手势等暂不纳入本轮整改
