# Feature Specification: Weavr 核心功能修复（存储 + 按钮 + 导出）

**Created**: 2026-07-24
**Status**: Draft
**Input**: 改进文件储存模式与各按钮点击，确保按钮点击后符合预期效果，文件正确储存与导出，文稿设定为 1 分钟保存一次

## Overview

Weavr PC 端三分栏布局的 UI 层在上一轮审查中已完成设计合规整改，但核心功能层面存在大量空壳：搜索框不工作、格式化工具栏（B/I/U/H1-H3/列表/引用）仅视觉装饰、查找替换全按钮无逻辑、撤销恢复未实现、写作模式（打字机/聚焦/沉浸）仅改变按钮颜色、"开始冲刺"无计时功能、AI 伴侣发送按钮和快捷问题全部丢弃用户输入。

同时，文稿自动保存机制为 800ms 防抖回调，频繁触发数据库写入且无错误处理。用户数据仅存于 SQLite 数据库，无任何导出能力——零 TXT、零 JSON、零 Markdown 导出。

本次功能目标：将所有非功能性按钮落地为有实际行为的交互，将自动保存改为 60 秒定时周期保存并增加错误重试与状态展示，建立 TXT/JSON/Markdown 三格式导出能力。

## User Scenarios & Testing

### User Story 1 — 可靠的定时自动保存 (Priority: P1)

作为写作用户，我不需要担心文稿丢失——系统每 60 秒自动将当前文稿保存到数据库，状态栏实时显示"已保存"/"保存中..."/"保存失败（点击重试）"。如果保存失败，系统自动重试最多 3 次，失败后提供手动重试入口。

**Why this priority**: 文稿数据安全是写作应用的生命线。当前 800ms 防抖机制无错误处理，一次数据库写入失败即静默丢失所有未保存内容。定时保存 + 错误恢复是底线功能。

**Independent Test**: 打开 Weavr 编辑任意文稿，观察状态栏在 60 秒周期内从"编辑中..."→"保存中..."→"已保存"。断开数据库连接模拟失败，观察"保存失败（点击重试）"出现并可通过点击重试恢复。

**Acceptance Scenarios**:

1. **Given** 用户正在编辑文稿, **When** 距离上次保存满 60 秒, **Then** 系统自动将当前内容写入数据库，状态栏显示"保存中..." → "已保存"
2. **Given** 自动保存正在进行中, **When** 用户继续输入, **Then** 输入不被阻塞，内容正常响应，保存完成后状态更新
3. **Given** 自动保存因数据库错误失败, **When** 失败发生, **Then** 状态栏显示"保存失败（点击重试）"，系统自动重试最多 3 次（间隔 5 秒）
4. **Given** 用户切换文稿标签, **When** 切换时当前文稿有未保存内容, **Then** 系统先触发一次即时保存再切换

---

### User Story 2 — 可用的搜索与查找替换 (Priority: P1)

作为写作用户，我在文稿列表中输入关键词能实时筛选匹配的文稿，在编辑器中打开查找替换栏后能搜索文本、在匹配项间跳转、替换单个或全部匹配项，并看到当前匹配序号（如"3/12"）。

**Why this priority**: 搜索和查找替换是长文稿编辑的核心需求。当前搜索框和查找栏是完全的空壳——用户输入后无任何响应。这是从"不可用"到"可用"的关键修复。

**Independent Test**: 在文稿列表搜索框输入文稿标题关键词 → 列表实时筛选；在编辑器中打开查找栏输入文本 → 编辑器跳到第一个匹配项并高亮，计数器显示"1/N"；点击替换 → 当前匹配项被替换并跳到下一个。

**Acceptance Scenarios**:

1. **Given** 文稿列表中有 10+ 篇文稿, **When** 用户在搜索框输入关键词, **Then** 列表实时筛选仅显示标题或内容片段匹配该关键词的文稿
2. **Given** 编辑器中打开查找替换栏, **When** 用户输入查找文本并按"下一个", **Then** 编辑器滚动到第一个匹配位置，计数器显示"1/N"
3. **Given** 查找已定位到某个匹配项, **When** 用户在替换输入框填入文本并点击"替换", **Then** 当前匹配项被替换，自动跳到下一个匹配项
4. **Given** 查找已定位且存在多个匹配项, **When** 用户点击"全部替换", **Then** 所有匹配项一次性替换，显示"已替换 N 处"
5. **Given** 查找栏打开且用户清空查找输入, **When** 查找文本为空, **Then** 计数器归零，无高亮，替换按钮禁用

### User Story 3 — 可用的文本格式化 (Priority: P1)

作为写作用户，我选中一段文本后点击 B/I/U 按钮能在文本前后插入对应的 Markdown 标记（`**粗体**`、`*斜体*`、`__下划线__`），点击 H1/H2/H3 能在当前行首插入对应级别的标题标记（`#`、`##`、`###`），点击引用/列表能给选中行添加 `>` 或 `- ` 前缀。撤销和恢复按钮能回退/前进最近的文本修改。

**Why this priority**: 格式化是文本编辑器的基础能力。当前工具栏所有按钮仅有视觉反馈而无任何文本操作——用户点击 B 后文稿内容不变。纯文本标记方案不依赖富文本组件，实现简单且兼容性好。

**Independent Test**: 在编辑区输入一段文字，选中部分文字点击"B"按钮 → 选中文字被 `**` 包裹。点击"H1" → 当前行首增加 `# `。连续点击"撤销" → 回退到初始状态。

**Acceptance Scenarios**:

1. **Given** 用户选中了一段文本, **When** 点击 B 按钮, **Then** 选中文本被 `**...**` 包裹，光标移到包裹后的位置
2. **Given** 光标在某个段落中, **When** 点击 H1 按钮, **Then** 该行首增加 `# ` 前缀（或已有 `#` 时切换为 `##`）
3. **Given** 用户选中多行文本, **When** 点击引用按钮, **Then** 每行首增加 `> ` 前缀
4. **Given** 用户进行了多次格式化操作, **When** 点击撤销按钮, **Then** 回退到上一个内容状态；点击恢复按钮前进到下一个状态
5. **Given** 无文本被选中, **When** 点击 B/I/U 按钮, **Then** 插入对应标记对（如 `****`）并将光标置于标记中间

### User Story 4 — 文稿导出（TXT + JSON + Markdown） (Priority: P2)

作为写作用户，我可以通过导出功能将当前文稿保存为 TXT 纯文本文件、Markdown 格式文件，或导出整个书库（含所有章节、人物、世界观、关系数据）为 JSON 备份文件。导出时系统弹出系统原生文件保存对话框，我选择目标位置并确认文件名。

**Why this priority**: 导出是数据安全闭环的关键一环。用户需要有办法将创作成果带出应用——无论是用于备份、跨平台迁移还是发布。

**Independent Test**: 在编辑区打开一篇文稿，点击导出 → 选择 TXT → 弹出系统保存对话框 → 保存后在文件管理器中打开确认内容完整。

**Acceptance Scenarios**:

1. **Given** 用户正在编辑一篇文稿, **When** 选择"导出为 TXT", **Then** 系统弹出文件保存对话框，默认文件名为文稿标题，保存后文件内容为去除标记的纯文本
2. **Given** 用户正在编辑一篇文稿, **When** 选择"导出为 Markdown", **Then** 系统弹出文件保存对话框，默认扩展名为 .md，保存后保留所有 Markdown 标记
3. **Given** 一个书库包含多章文稿及人物/世界观/关系数据, **When** 选择"导出书库（JSON）", **Then** 系统弹出文件保存对话框，保存后 JSON 文件包含完整的结构化数据
4. **Given** 导出过程中发生文件写入错误, **When** 错误发生, **Then** 用户看到明确的错误提示"导出失败：文件无法写入"，而非静默失败

### User Story 5 — 写作增强功能（模式 + 冲刺 + Rail 导航） (Priority: P2)

作为写作用户，我可以开启打字机模式使编辑区自动滚动保持当前行居中；开启聚焦模式使非当前段落变暗；开启沉浸模式隐藏侧栏和文稿列表仅显示编辑器；点击"开始冲刺"启动 25 分钟倒计时并在状态栏显示剩余时间；侧栏折叠后的 Rail 图标点击后能实际切换文库分类。

**Why this priority**: 这些功能会影响专注写作体验，但不如保存、搜索、格式化那样是"不可用→可用"的底线修复。其中 Rail 图标导航缺失属于 UX 缺陷。

**Independent Test**: 点击"打字机"→ 输入多行后观察自动滚动；点击"聚焦"→ 观察非当前段落变暗；点击"开始冲刺"→ 状态栏显示倒计时；折叠侧栏后点击 Rail 上的"★"图标 → 切换到收藏文库。

**Acceptance Scenarios**:

1. **Given** 打字机模式已开启, **When** 用户在当前行继续输入, **Then** 编辑器自动滚动使当前行保持在可视区域的垂直中心
2. **Given** 聚焦模式已开启, **When** 用户在某段落中输入, **Then** 当前段落正常显示，其他段落透明度降低（约 0.3）
3. **Given** 沉浸模式已开启, **When** 进入沉浸模式, **Then** 侧栏和文稿列表面板收起隐藏，仅显示编辑区；退出沉浸模式后恢复
4. **Given** 用户点击"开始冲刺", **When** 冲刺启动, **Then** 工具栏中显示倒计时（初始 25:00），每秒递减，到 0 时提示"冲刺完成！"
5. **Given** 侧栏折叠为 56vp Rail, **When** 用户点击"★"图标, **Then** 文稿列表切换到收藏分类，Rail 上的"★"图标显示蓝色激活指示

---

### User Story 6 — AI 伴侣交互占位 (Priority: P3)

作为用户，我在写作伴侣中输入问题并点击发送后，能看到明确的"AI 功能开发中，敬请期待"提示，而非输入被静默丢弃。四个快捷提问按钮同样给出友好提示而非回显问题文本。

**Why this priority**: 所有按钮功能修复的一部分。AI 后端不在本轮范围，但当前静默丢弃用户输入的行为不可接受——用户会反复尝试而不理解为何无响应。

**Independent Test**: 在写作伴侣输入文本点击发送 → 消息列表中出现"写作伴侣：AI 功能开发中，敬请期待"；点击快捷按钮 → 同样提示。

**Acceptance Scenarios**:

1. **Given** 写作伴侣面板已打开, **When** 用户输入文本并点击发送, **Then** 消息列表中用户消息正常显示，AI 回复显示"AI 功能开发中，敬请期待"
2. **Given** 写作伴侣面板已打开, **When** 用户点击任意快捷提问按钮, **Then** 消息列表中显示"AI 功能开发中，敬请期待"

### Edge Cases

- **保存期间应用退出**: 应用进入后台或销毁前检查是否有未保存内容，如有则尝试最后一次即时保存
- **空文稿保存**: 内容为空时跳过保存，不触发"保存失败"
- **极长文稿查找**: 文稿超过 50,000 字符时，查找替换使用正则匹配，性能 < 200ms
- **格式化边界**: 光标在文本边界（开头/结尾）时，插入标记的位置逻辑正确，不产生孤立标记
- **撤销栈溢出**: 撤销历史最多保存 100 次操作，超出时丢弃最早的记录
- **导出空书库**: 书库无内容时导出 JSON 仍然生成有效 JSON（空数组），不报错
- **导出文件名冲突**: 系统文件保存对话框由 OS 处理重名冲突，应用不介入
- **60 秒定时器与组件生命周期**: 切换文稿、退出编辑区时必须清除旧定时器，重新开始新文稿的 60 秒周期

## Requirements

### Functional Requirements

- **FR-001**: 系统必须每 60 秒自动保存当前编辑的文稿内容到数据库，无论用户是否在输入
- **FR-002**: 自动保存失败时必须自动重试最多 3 次（间隔 5 秒），3 次均失败后状态栏显示"保存失败（点击重试）"
- **FR-003**: 用户切换文稿标签时，如前文稿有未保存修改，必须触发一次即时保存
- **FR-004**: 文稿列表搜索框必须支持按标题和内容片段实时筛选匹配的文稿
- **FR-005**: 查找替换栏必须支持文本搜索、匹配项计数（如"3/12"）、上下导航、单个替换和全部替换
- **FR-006**: 格式化按钮（B/I/U/H1/H2/H3/引用/列表）必须对选中文本或当前行插入对应的 Markdown 标记
- **FR-007**: 撤销和恢复按钮必须维护最近 100 次内容修改的完整历史栈
- **FR-008**: 系统必须支持将当前文稿导出为 TXT 纯文本格式，通过系统文件保存对话框选择目标位置
- **FR-009**: 系统必须支持将当前文稿导出为 Markdown 格式
- **FR-010**: 系统必须支持将整个书库（章节+人物+世界观+灵感+关系）导出为一个 JSON 备份文件
- **FR-011**: 打字机模式激活时必须自动滚动编辑区使当前光标所在行保持在可视区域垂直中心
- **FR-012**: 聚焦模式激活时必须降低非当前段落透明度至约 0.3
- **FR-013**: 沉浸模式激活时必须隐藏侧栏和文稿列表面板
- **FR-014**: 冲刺功能必须提供 25 分钟倒计时，在状态栏显示剩余时间，到 0 时提示完成
- **FR-015**: 侧栏折叠 Rail 图标必须可点击并切换到对应的文库分类
- **FR-016**: AI 写作伴侣的发送按钮和快捷提问必须显示"AI 功能开发中，敬请期待"提示

### Key Entities

- **保存状态 (SaveState)**: 枚举 — Idle（已保存）、Saving（保存中）、Failed（失败可重试）、Retrying（第 N 次重试中）
- **编辑历史 (EditHistory)**: 栈结构，存储最近 100 次编辑器内容快照（字符串），支持 push（记录修改）、undo（回退）、redo（前进）
- **导出格式 (ExportFormat)**: 枚举 — TXT（纯文本）、MD（Markdown）、JSON（结构化备份）

## Success Criteria

### Measurable Outcomes

- **SC-001**: 文稿内容在 60 秒内自动持久化，定时误差 < 2 秒
- **SC-002**: 保存失败后用户可在状态栏看到明确错误信息，点击重试成功率 ≥ 99%（排除磁盘满等硬件故障）
- **SC-003**: 文稿搜索在输入关键词后 200ms 内完成筛选并更新列表
- **SC-004**: 查找替换在 50,000 字符文稿中完成全文搜索 < 200ms
- **SC-005**: 100% 的格式化按钮点击后编辑器内容产生可见的变化
- **SC-006**: 撤销可连续回退最近 100 次操作，每次回退 < 50ms
- **SC-007**: TXT/MD/JSON 三种格式均能成功导出，导出文件可在系统文件管理器中打开且内容完整
- **SC-008**: 打字机模式下当前行始终在可视区域内
- **SC-009**: 点击所有 Rail 图标后文库列表正确切换到对应分类
- **SC-010**: 发送 AI 消息后用户收到明确的"功能开发中"提示，而非输入被丢弃

## Assumptions

- 文稿当前为纯文本编辑（TextArea），格式化基于 Markdown 标记语法，不需要富文本渲染
- 查找替换基于纯字符串匹配（indexOf），不使用正则表达式（避免正则注入和复杂转义）
- 导出使用 HarmonyOS `picker.DocumentViewPicker.save()` API 调用系统文件保存对话框，文件 I/O 使用 `@kit.CoreFileKit` 的 `fileIo`
- 定时器使用 ArkTS 全局 `setInterval` / `clearInterval`，组件销毁时在 `aboutToDisappear` 中清理
- AI 后端对接不在本轮范围，本轮仅实现占位提示
- 所有改动仅限 PC 布局组件（pclayout/），不涉及手机/平板端
- 自动保存的基础设施（ChapterDao.updateContent、DatabaseHelper）已存在且工作正常
