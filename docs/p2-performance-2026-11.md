# P2 性能记录（2026-11）

- 起点：`4e9c279`（P1 完成）
- 本阶段只做**能在本机静态验证**的两项；另外两项（排版行回收、画布命中）明确延后，原因见 §3。
- 没有设备，**帧率与输入延迟一个数字都没有测**，下面只写代码层面的结论。

## 1. 改了什么

### D-06 主列表虚拟化（文稿列表）

原来 `DocListPane` 是 `List + ForEach(this.visibleItems())`：每次 build 都会把**全部**文稿行建出来，
切项目 / 切文库 / 搜索 / 改一篇摘要都会整列重建。现在：

- 新增 [DocItemSource.ets](entry/src/main/ets/shell/DocItemSource.ets)：`IDataSource` 实现，
  只按需 `getData(index)`；整体替换时 `reload()` 调 `onDataReloaded()`。
- `DocListPane` 用 `LazyForEach(this.docSource, …)`，并用 `@Local projectWatch: ProjectStore = app.project`
  + `@Monitor('projectWatch.docItems')` 在数组被整体替换时重取投影；搜索框 onChange 也同步重投影。
- 行内字段（标题/摘要/字数/选中态）仍是 `@ObservedV2 + @Trace` 就地更新，**不需要**通知数据源。

保留的边界：
- 空态仍用 `visibleCount()` 判断；`visibleItems()` 仍是唯一投影来源（搜索规则没变）。
- `enableLongTake` 的 `id('doc_row_…')` 仍在：点击的行必然已渲染，一镜到底不受影响；
  但**离屏行不再存在于组件树**，任何"按 id 找行"的新逻辑必须自己处理找不到的情况。

### D-07（部分）字数统计不再重复扫描

- `EditorStore.wordCount` 增加缓存：正文引用没变就直接返回上次结果。
  这一处被标题栏、中栏、状态条**同一帧内各读一次**，原来每次都要把整篇过一遍。
- `ProjectStore.updateDocPreview` 每键都会调；新增 `countOf()` 缓存，同一个正文只数一次。

效果：一次按键从「中栏 1 次 + 状态条 1～2 次 + 保存路径 1 次」压到「内容变化后各数一次」。
50k 字下 `countChars` 是一次紧循环（无分配），但每帧重复十几次仍是白描开销。

## 3. 明确延后（连同理由与再启动条件）

| 项 | 为什么这轮不做 | 再启动条件 |
| --- | --- | --- |
| `LayoutCache` 已排行回收 | 行数组同时被滚动上限、光标 y、打字机焦点、锚点恢复、选区手柄共用；改成"只保留视口窗口"要重写偏移换算，**在没有设备的情况下无法验证**，一旦算错就是整篇错位 | 有设备能跑 `docs/flowtext-testing.md` 的 12 项手工清单后，先加"行窗口"断言再改 |
| `TextLayoutEngine.wordRangeAt` 为整篇建排版 | 只在**双击选词**时触发（不是每键），且要处理段落切片后的偏移回映射；收益小、回归面大 | 先做一次真机双击耗时采样；若 >16ms 再做 |
| 画布命中 `O(卡×行)` | 拖拽时每帧都要跑，但当前卡片规模（<100）下是纯矩形比较，未测出问题；优化前需要真实帧数据 | 真机 80 卡拖拽采样后再决定是否加空间索引 |
| 46 条 `Function may throw` | 属"代码质量"而非性能，且需要逐处判断是否真的会抛；混在性能阶段做会放大回归面 | 与 P4/P5 触碰这些文件时顺手补 |

## 4. 一句话结论

列表与字数是**本机能证伪的两处确定开销**，已修并有守卫；另外三处要么只在低频路径，要么必须靠设备数据判断，写在上面等真机。
