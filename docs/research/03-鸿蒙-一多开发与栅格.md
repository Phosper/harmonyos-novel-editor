## 一、结论摘要（可直接执行）

1. **断点取值不用改**：官方横向断点为 `xs(0,320) / sm[320,600) / md[600,840) / lg[840,1440) / xl[1440,+∞)` vp，Weaver 的 600/840 正好落在官方 md/lg 边界上，无需调整数值。[D12:L46-54]
2. **断点必须由「窗口宽度」决定，不能由设备类型 / 屏幕方向 / 是否可折叠决定**——CodeLinter 有专门规则硬性拦截后者。[D12:L68][D24:L1646][D26]
3. **改用系统断点 API 取断点**：`UIContext.getWindowWidthBreakpoint()/getWindowHeightBreakpoint()`（API 13+），或在 `@ComponentV2` 中用 `@Env(SystemProperties.BREAK_POINT)`（API 22+）；不要再自己写 `matchMediaSync('(min-width:840vp)')`。[D23:L2693-2747][D25:L5,L14][D12:L98-104]
4. **断点刷新挂在 `window.on('windowSizeChange')`**；折叠开合**不要**用 `display.on('foldStatusChange')` 驱动布局。[D08:L59-66][D16:L189-192]
5. **三栏工作台不要用 `GridRow`**：官方明文把「三分栏」归给 `SideBarContainer + Navigation + 断点`，把 `GridRow/GridCol` 归给「挪移布局 / 缩进布局」。[D14:L9-20][D15:L288-334]
6. **`GridRow` 真正的收益点是中心编辑区的「缩进布局」**（宽屏正文居中留白）：官方模板 `columns sm4/md8/lg12` + `span sm4/md6/lg8` + `offset md1/lg2`。[D15:L645-676]
7. **若用栅格就别再手写列数**：API 20 起 `columns` 默认值就是官方推荐列数 `{xs:2, sm:4, md:8, lg:12, xl:12, xxl:12}`。[D21:L43][D03:L117-119]
8. **「固定宽度侧栏 + 弹性主区」用 `layoutWeight`/百分比即可**，这是官方认可的「占比能力」；栅格列宽由系统等分计算、不允许手配，表达不了「固定 230vp 侧栏」。[D11:L252-273][D12:L596]
9. **多端差异优先用资源限定词目录**（`resources/tablet`、`resources/2in1`），但 **base 目录必须留默认值**。[D18:L30-34][D06:L83-105]
10. **分屏 / 悬浮窗 / 自由多窗**必须同时监听 `windowStatusChange` + `windowSizeChange`，并把可能溢出的内容包进 `Scroll`（上下分屏高度会减到约 1/2）。[D16:L94-116][K01]
11. **把 `plugin:@cross-device-app-dev/recommended` 加进 `code-linter.json5`**，让一多的坑自动报出来（当前 Weaver 只启用了 performance 与 typescript-eslint）。[D26-D33]
12. **明确结论：不应把 Weaver 的三栏外壳整体改写成官方栅格系统**；应改的是「断点的来源」（换成官方 API）与「把栅格/官方容器用到正确的局部」。理由与代价见第九节。

## 二、一多开发能力框架（附文档 id）

### 2.1 三个基础问题 → 三层能力

官方先提出实现「一套代码工程，一次开发上架，多端按需部署」要解决的三个基础问题：页面如何适配不同屏幕尺寸与色彩风格、功能如何兼容不同设备的系统能力（NFC/SIM 等）、如何组织代码工程。[D07:L30-34]

对应三层能力（这是官方对「一多」的分层答案）：[D07:L36-40]

| 层 | 官方定义 | 关键抓手 |
| --- | --- | --- |
| **工程级一多** | 应用采用三层架构设计，结合工程管理与包管理能力，实现工程代码的统一管理与多设备按需部署 | common / features / products 三层工程；部署模型 A/B [D07:L220-262][D07:L292-322][D09:L9-42] |
| **功能级一多** | 在工程级一多基础上，通过 API Capability 绑定机制提升功能模块灵活性与代码复用率 | SysCap 要求集 / 联想集 / 设备支持集 [D07:L111-117] |
| **界面级一多** | 在功能级一多支撑下，依托 UI 一多能力（典型布局、响应式与自适应布局）+ 统一视觉与交互设计 | 自适应布局 + 响应式布局 + 交互归一 [D07:L84-108][D10][D19] |

「界面级一多」内部又拆成三块官方建议：
- **窗口适配**：横竖屏切换策略、沉浸式适配、PC/2in1 自由窗口适配。[D07:L86-94]
- **断点和响应式布局**：以窗口宽度划分断点，跨断点时改变页面布局（单列→双列→三列）。[D07:L96-100]
- **交互归一**：把触摸 / 鼠标 / 键盘 / 遥控器的底层事件抽象为标准化事件，开发者只调统一接口。[D07:L102-108][D19:L34-40]

### 2.2 官方的「例外」声明（重要）
- 小屏幕（如手表）与屏幕比例特殊场景（如 Pura X 外屏）**无法用一套布局适配**，需单独设计 UX 并单独出 HAP。[D07:L44-46][D13:L710]
- 多数场景下页面复杂度过高时，用一套代码直接实现的成本高、可读性差，此时应**单独设计 UX + 用 if-else 断点单独实现一套布局**。[D07:L46]
- UX 设计原则应覆盖「差异性、一致性、灵活性、兼容性」四点。[D07:L60][D20:L14]

### 2.3 部署模型选择
- **部署模型 A**：一次编译生成**相同**的 HAP；**部署模型 B**：一次编译生成**不同**的 HAP。[D07:L294-298]
- **相同泛类设备优先 A，不同泛类优先 B**；泛类按「屏幕尺寸、输入方式、交互距离」划分（手机+平板 / 车机+智慧屏 / 智能穿戴）。[D07:L303-320]
- 目标设备较多时通常是 A+B 混用；但**不管哪种都必须一次编译**。[D07:L322-324]

## 三、断点与栅格

### 3.1 断点取值（官方推荐值）

**横向断点**（以应用窗口宽度为判断条件）：[D12:L46-54]

| 断点 | 窗口宽度（vp） | Weaver 现状 |
| --- | --- | --- |
| xs | (0, 320) | 未区分 |
| sm | [320, 600) | `BreakPoint.SM`（<600）一致 |
| md | [600, 840) | `BreakPoint.MD`（600–840）一致 |
| lg | [840, 1440) | `BreakPoint.LG`（≥840，未再切 1440）未区分 xl |
| xl | [1440, +∞) | 缺失 |

**纵向断点**（以窗口高宽比判断）：`sm (0,0.8) / md [0.8,1.2) / lg [1.2,+∞)`。[D12:L56-62]

关键规则：
- **断点面向窗口而非设备类型**；同一设备的不同窗口形态（全屏/分屏/自由窗口）可能落入不同断点，展示不同布局。[D12:L68]
- 同一设备横竖屏旋转也会改变断点（如 Mate60 竖屏 sm、横屏 md）；部分机型（Pura70 Pro/Ultra、Pocket 2、nova Flip、Mate 70 Air）横屏会落进 lg。[D12:L69]
- 开发者可按场景只适配部分断点；xl 之后可自行增加 xxl 等断点。[D12:L70-71]
- 官方给出「常见设备型号 → 全屏尺寸 → 横/纵断点」对照表，仅用于**设计阶段选型**（例如手机竖屏=sm/lg、平板横屏=lg/sm、PC=MateBook Pro 1642×1094 为 xl/sm），**不是运行时判据**。[D12:L73-92]

### 3.2 断点由谁决定 + 官方断点 API

| 获取方式 | API / 装饰器 | 起始版本 | 说明 |
| --- | --- | --- | --- |
| `UIContext.getWindowWidthBreakpoint()` | 返回 `WidthBreakpoint` | **API 13+** | 按窗口宽度 vp 返回枚举 [D23:L2693-2732][D24:L1636-1654] |
| `UIContext.getWindowHeightBreakpoint()` | 返回 `HeightBreakpoint` | **API 13+** | 按窗口高宽比返回枚举 [D23:L2742-2787][D24:L799-815] |
| `@Env(SystemProperties.BREAK_POINT)` | 装饰 `uiObserver.WindowSizeLayoutBreakpointInfo` | **API 22+** | 窗口尺寸变化时自动触发关联组件刷新；`@ComponentV2` 下可用 `UIUtils.addMonitor` 监听 `widthBreakpoint/heightBreakpoint` [D25:L5,L14,L289,L300-323][D12:L98-105] |
| `mediaquery.matchMediaSync('(840vp<=width)')` | 自查字符串 | API 8+ | 官方在响应式布局最佳实践中仍给了 `BreakpointSystem` 范例（内置阈值 320/600/840） [D12:L410-526][D01:L104-134] |
| `GridRow({ breakpoints })` | 组件级 | API 9+ | 默认 `{value:['320vp','600vp','840vp'], reference: WindowSize}`，最多 6 个断点 [D21:L45,L129-141] |

枚举值定义（官方权威取值）：[D24:L1650-1654][D24:L813-815]

```
WIDTH_XS=0   <320vp          HEIGHT_SM=0  高宽比 <0.8
WIDTH_SM=1   [320,600)       HEIGHT_MD=1  [0.8,1.2)
WIDTH_MD=2   [600,840)       HEIGHT_LG=2  ≥1.2
WIDTH_LG=3   [840,1440)
WIDTH_XL=4   ≥1440
```

- 断点阈值**个别设备由系统产品化配置调整**，所以「自己写死 600/840」比自己取系统断点更容易漂移。[D24:L1646]
- 官方提供的推荐写法：在 `UIAbility.onWindowStageCreate` 的 `loadContent` 回调后取一次断点，注册 `mainWindow.on('windowSizeChange')`，回调中重新 `getWindowWidthBreakpoint()` 并写 `AppStorage`，UI 侧用 `@StorageLink` 消费。[D12:L107-220][D16:L136-158][D08:L89-96]
- **断点阈值没有以系统资源（`$r('sys.float.*')`）形式暴露**：本地文档中未找到「断点阈值作为资源引用」的能力，断点只通过上表四种形式提供。

### 3.3 栅格系统（GridRow / GridCol）

#### 3.3.1 基础语义
- 栅格系统「把页面水平方向划分为等宽的列」，样式由 **Margin / Gutter / Columns** 三个属性决定；**单个 Column 的宽度由系统结合三者自动计算，不需要也不允许开发者手动配置**。[D12:L577-596][D03]
- 官方采用 **12 列设计**，因为 12 可被 2/3/4/6 整除，布局可能性更灵活。[D12:L581]
- 基础单位是 **8vp 网格**，更小的控件（图标）可对齐 4vp；Margin/Gutter 的值应参考 8vp/4vp 网格设置（如手机基础栅格 Margin 24vp、卡片栅格 Margin 12vp）。[D12:L618]
- **官方推荐列数与间距取值**：[D12:L620-629]

| 参数项 | 手机 | 折叠屏 | 平板 | 车机 | 智慧屏 |
| --- | --- | --- | --- | --- | --- |
| 竖屏栅格数 | 4 | 8 | 8 | – | – |
| 横屏栅格数 | 8 | 8 | 12 | 12 | 12 |
| 基础栅格 Margin（vp） | 24 | 24 | 24 | 24 | 48 |
| 基础栅格 Gutter（vp） | 24 | 24 | 24 | 24 | 24 |
| 卡片栅格 Margin（vp） | 12 | 12 | 12 | 12 | 48 |
| 卡片栅格 Gutter（vp） | 12 | 12 | 12 | 12 | 24 |

> 注意两张表的口径不同：上表是**按设备类型**的 UX 设计规范；而组件层按**断点**给列数，API 20 起 `columns` 默认 `{xs:2, sm:4, md:8, lg:12, xl:12, xxl:12}`，示例代码普遍写 `{sm:4, md:8, lg:12}`。[D21:L43][D03:L119][D12:L801]

#### 3.3.2 GridRow 参数表

| 参数 | 类型 | 默认值 | 含义 |
| --- | --- | --- | --- |
| `columns` | `number \| GridRowColumnOption` | API20 前 12；API20 起 `{xs:2,sm:4,md:8,lg:12,xl:12,xxl:12}` | 布局列数 [D21:L43] |
| `gutter` | `Length \| GutterOption{x,y}` | 0（单位 vp） | 列间距（x）与折行行间距（y） [D21:L44,L58-61] |
| `breakpoints` | `BreakPoints{value, reference}` | `{value:['320vp','600vp','840vp'], reference: WindowSize}` | 断点阈值数组 + 参照物；数组必须单调递增 [D21:L45,L129-141] |
| `direction` | `GridRowDirection` | `Row` | **只支持 Row / RowReverse**，不支持 Column 方向 [D21:L46,L158-182] |
| `alignItems` | `ItemAlign`（API 10+） | `Start` | GridCol 在主轴垂直方向的对齐 [D21:L188-206] |
| `onBreakpointChange` | `(bp: string) => void` | – | 断点变化回调，bp ∈ xs/sm/md/lg/xl/xxl；**当 reference=ComponentSize 时，不建议在回调中动态改 GridRow 的 padding/margin** [D21:L212-230] |

`BreakpointsReference`：`WindowSize=0`（以窗口为参照，默认）/ `ComponentSize=1`（以容器自身为参照）。官方态度：**「考虑到应用可能以非全屏窗口的形式显示，以应用窗口宽度为参照物更为通用」**。[D21:L143-156][D03:L63]

#### 3.3.3 GridCol 参数表

| 参数 | 类型 | 默认值 | 含义 |
| --- | --- | --- | --- |
| `span` | `number \| GridColColumnOption` | 1 | 占据列数；**span=0 表示不参与布局计算、不渲染** [D22:L41] |
| `offset` | `number \| GridColColumnOption` | 0 | 相对于前一个栅格子组件偏移的列数 [D22:L42] |
| `order` | `number \| GridColColumnOption` | 0 | 排序序号，从小到大排列 [D22:L43] |

继承规则：`span`/`offset`/`order` 按 `xs→sm→md→lg→xl→xxl` **向后继承**（不支持向前继承）。例如只配 `span:{sm:3}`，则 md 也取 3。[D12:L900][D22:L45]
折行规则：子组件 span 之和超过总列数时**自动换行**；单个 span 超过最大列数时后台按最大列数处理。[D21:L164-170]
禁用项：`span`/`offset` **不建议使用小数**。[D28]

#### 3.3.4 断点不同时列数怎么变（两种官方写法）
1. **改 `columns`**：`GridRow({ columns: { sm: 4, md: 8, lg: 12 }, gutter: { x: {sm:8,md:16,lg:24}, y: {sm:8,md:16,lg:24} } })`，子组件 `GridCol({ span: {sm:2,md:2,lg:2} })`。[D12:L800-818]
2. **只改 `span`**（`columns` 固定 12）：`GridCol({ span: { xs:12, sm:6, md:4, lg:3 } })`，等价于「屏幕越大一行放越多」。[D12:L910-946][E05:L16-18]

推荐做法：**手动配置各断点列数**，不要依赖系统补全（避免补全结果不符合预期）。[D21:L81]

## 四、自适应手段对比表

官方把方法分为**自适应布局**（随容器连续变化）与**响应式布局**（随断点/特征不连续变化）两大类：**自适应布局多用于解决页面各区域内的布局差异，响应式布局多用于解决页面各区域间的布局差异**。[D10:L7-10]

### 4.1 响应式布局的四种能力（官方表）[D12:L17-22]
| 能力 | 官方定义 |
| --- | --- |
| 断点 | 将窗口宽度划分为不同范围，监听窗口尺寸变化，断点改变时同步调整布局 |
| 媒体查询 | 监听窗口宽度、横竖屏、深浅色、设备类型等多种媒体特征 |
| 栅格 | 把所在区域划分为有规律的多列，调整不同断点下参数与子组件占列数 |
| 响应式组件 | Tabs / Swiper / Grid / List / GridRow，通过断点设置不同展示效果 |

### 4.2 手段对比表

| 手段 | 适用场景 | 代价 | 官方态度 |
| --- | --- | --- | --- |
| 百分比宽高 | 子组件按父容器比例伸缩（占比能力） | 极低 | 推荐；比 `layoutWeight` 更常用 [D11:L256-266] |
| `layoutWeight` | 兄弟组件按权重分配主轴空间 | 低 | 推荐但**有使用限制**：仅父容器为 Row/Column/Flex 生效；设置后组件自身尺寸失效（`.width('40%')` 会被覆盖）[D11:L260-266] |
| `Flex` 的 `flexGrow/flexShrink/flexBasis` | 拉伸能力：剩余/不足空间定向分配 | 低 | 推荐，常与 flexBasis 搭配 [D11:L21-27] |
| `Blank` 组件 | 仅空白区域伸缩 | 极低 | 仅父为 Row/Column/Flex 时生效 [D11:L29] |
| `justifyContent: SpaceEvenly` | 均分能力（工具栏、底部菜单） | 极低 | 推荐 [D11:L165-167] |
| `aspectRatio` | 缩放能力：保持宽高比 | 极低 | 推荐，配合百分比布局使用 [D11:L352] |
| `displayPriority` | 隐藏能力：按优先级随尺寸增删元素 | 低 | 「比较高级的布局方式」，用于分辨率差异大的场景 [D11:L585-589] |
| `FlexWrap.Wrap` | 折行能力：横放不下就换行 | 低 | 推荐（横竖屏/手机→平板切换常客）[D11:L687-691] |
| `constraintSize` | 约束内容最大/最小尺寸（如弹窗 maxHeight 90%） | 低 | 推荐用于小方形屏弹窗防截断 [D13:L499-518] |
| `GridRow/GridCol` | 挪移布局（图文左右↔上下）、缩进布局（单列列表居中留白）；页面整体或局部均可 | **中**：增加组件树节点；用错（span 恒等于 columns）纯属浪费 [D27] | 推荐但**必须用对场景** [D14:L149-178][D15:L469-514][D15:L639-676] |
| 媒体查询 `mediaquery` | 监听窗口宽高、横竖屏、深浅色、device-type、圆形屏等 | 中 | 官方给了断点监听范例，但新代码更推荐系统断点 API [D01:L104-134][D12:L396-473] |
| `display` 监听 | 屏幕方向、折叠状态、显示模式变化 | 中 | **不用于页面布局的响应式与接续** [D08:L61-63] |
| 资源限定词目录 | 各端差异化的尺寸/颜色/文案/图片 | 中（改动面广） | 推荐；base 必须留默认值 [D18:L34][D06:L83-105] |
| `Grid` / `List.lanes` / `Swiper.displayCount` / `Tabs.vertical` | 重复布局、轮播、底部↔侧边导航 | 低-中 | 推荐（响应式组件）[D14:L24-147][D15:L30-159] |
| `SideBarContainer` | 侧边栏（二分栏）：`showSideBar`、`sideBarWidth`、`SideBarContainerType(Overlay/Embed)`、可拖拽调宽 | 中 | 侧边栏场景的官方首选 [D14:L83-97][D15:L165-204] |
| `Navigation.mode` | 单/双栏；导航栏可控制内容区路由跳转 | 中 | 官方首选（并推荐 Router→Navigation 迁移）[D14:L99-111][D15:L206-230][D04:L9] |
| `SideBarContainer + Navigation` | **三分栏** | 中-高 | 官方对三分栏的唯一推荐组合 [D14:L15-17][D15:L288-334] |
| `ContainerReader` | **容器级断点**（按组件自身尺寸而非窗口尺寸） | 中 | 可用，但**API 26.0.0 起**才支持 [D02:L3,L16-22] |

### 4.3 官方给出的四种「响应式布局样式」及其适用条件 [D12:L1136-1166]
- **分栏布局**：导航栏与内容区同屏左右显示；**当横向 vp ≥ 600vp 时显示分栏**。
- **重复布局**：相同属性组件横向并列；适用于**对宽高比敏感的图片和组合内容**，即内容放大后会超过原图 150% 的场景。
- **挪移布局**：上下布局↔左右布局；适用于横竖屏切换及**宽高比明显变化（>200%）**且需保证内容完整的场景。
- **缩进布局**：宽屏上内容居中留白；适用于纯段落文本 / 上图下段落 / 卡片结构；**栅格为 8 或 12 列时，用 6 列和 8 列的缩进**。

### 4.4 「栅格 vs 手写 Flex/百分比」的官方分界
- **该用栅格**：把窗口整体或某个容器「按列数对齐」的场景——图文挪移、单列列表缩进、按断点改变一行元素个数。[D15:L469-514][D15:L639-676][E05]
- **不该用栅格**：区域之间「固定 + 弹性」的组合（侧栏固定宽、主区吃掉剩余）。官方三分栏示例里，`SideBarContainer` 的宽度用 `80%/50%/20%`、`Navigation` 的 `navBarWidth` 用 `50%/40%/30%`，**没有用 GridRow 去分这三栏**。[D15:L173][D15:L202][D15:L296][D15:L326]
- **不该用栅格（性能视角）**：所有 `GridCol` 的 `span` 都等于父组件 `columns` —— 「等效于子组件宽度始终为父容器的 100%，栅格系统没有发挥作用，徒增页面组件树复杂度，影响性能」。[D27]
- 官方对「三栏式工作台」的直接答案：`SideBarContainer`（第一栏）+ `Navigation`（第二、三栏）+ 断点控制 `showSideBar` 与 `mode`；并对「单栏时该优先展示哪一栏」按**内容重要性**判断（邮箱单栏优先内容区、日历单栏优先导航区）。[D15:L288-334][D15:L347][D15:L411-413]
- `Navigation` 与 `SideBarContainer` 的分工：**导航栏能控制内容区的路由跳转（列表↔详情）用 Navigation；侧栏通常不控制内容区内容（图文详情与评论区）用 SideBarContainer**。[D15:L230]
- `Navigation` 分栏相关接口：`mode`（Stack/Split/Auto/AUTO_WITH_ASPECT_RATIO）、`navBarWidth`、`navBarWidthRange`、`minContentWidth`、`enableDragBar`、`hideNavBar`、`splitPlaceholder`、`enableModeChangeAnimation`。[D04:L9-67]

## 五、多设备资源与限定词

### 5.1 目录命名规则（官方表）[D06:L85-105]

组合顺序：`移动国家码_移动网络码-语言_文字_国家或地区-横竖屏-设备类型-颜色模式-屏幕密度`
连接方式：MCC/MNC 之间、语言/文字/地区之间用下划线；其他限定词之间用中划线。

| 限定词 | 取值 |
| --- | --- |
| 横竖屏 | `vertical`（竖屏）/ `horizontal`（横屏） |
| **设备类型** | `phone` / `car` / `tablet` / `tv` / `wearable` / **`2in1`** |
| 颜色模式 | `dark` / `light` |
| 屏幕密度 | `sdpi / mdpi / ldpi / xldpi / xxldpi / xxxldpi` |
| 语言/文字/地区 | `zh / Hans / CN` 等（ISO 639 / 15924 / 3166-1） |

示例：`en_GB-vertical-car-mdpi`、`zh_CN-car-ldpi`。[D06:L22][D06:L89]

### 5.2 支持差异化的资源类型
`element`（boolean / color / float / integer / intarray / plural / strarray / string）、`media`、`profile` 支持限定词目录；**`rawfile` 与 `resfile` 不参与设备状态匹配**（原始文件直出）。[D06:L48-61][D06:L472][D18:L30]

### 5.3 匹配规则与官方建议
- 匹配优先级（高→低）：`MCC/MNC > 区域(语言/文字/地区) > 横竖屏 > 设备类型 > 颜色模式 > 屏幕密度`。[D06:L478]
- 先找匹配的限定词目录，找不到才回落到 `base`。[D06:L472][D18:L30]
- **「强烈建议对于所有应用自定义资源都在 base 目录中定义默认值，防止出现找不到资源值的异常场景。」** [D18:L34]
- AppScope 资源会合入模块资源，同名冲突时优先级：AppScope > HAP 自身 > 依赖 HAR（HAR 之间按 oh-package 依赖顺序，靠前优先）。[D06:L39]
- 系统资源（分层参数，`$r('sys.type.name')`）：同一资源 ID 在设备类型、深浅色等不同配置下取值不同；**系统预置应用强烈建议使用系统资源，三方应用可选**。[D18:L104-112][D06:L452-458]

### 5.4 「用资源做差异」还是「用代码判断」？
官方立场是**两者分工，但判据必须是窗口/断点**：
- **视觉量（尺寸、间距、字号、颜色、图片）→ 用资源限定词目录做差异**，官方示例就是建 `tablet` 限定词目录、让同一 `$r('app.float.my_float')` 在默认设备=60vp、平板=80vp。[D18:L70-101]
- **布局结构（单栏/双栏/三栏、底部↔侧边导航）→ 用断点判断**；用设备类型 / 是否可折叠做布局判据会被 CodeLinter 拦。[D26]
- 但要区分：窗口形态不同不代表设备不同，官方强调「页面适配不同尺寸屏幕的本质，是适配不同尺寸的窗口」——「通过一次性基于断点的布局适配，即可支持分屏、悬浮窗、自由窗口等多种窗口模式」。[D08:L18]

## 六、窗口形态变化与监听（含时序坑）

### 6.1 窗口模式与配置
- 三种窗口模式：全屏 / 分屏（二分屏）/ 自由悬浮多窗（自由多窗 + 悬浮窗）。[D16:L5-13]
- `module.json5 > abilities > supportWindowMode` 取值 `fullscreen / split / floating`，默认三者全支持。[D16:L19-27]
- 设备支持矩阵：手机（全屏/分屏/悬浮窗，无自由多窗）、平板（含自由多窗）、电脑（自由多窗为默认）。[D16:L58-65]
- 自定义支持横向悬浮窗：`preferMultiWindowOrientation: landscape`。[K02]

### 6.2 监听接口与分工 [D08:L68-83]

| API | 用途 |
| --- | --- |
| `getWindowWidthBreakpoint()` / `getWindowHeightBreakpoint()` | 取当前窗口横/纵断点 |
| `window.on('windowSizeChange')` / `off` | **布局刷新唯一推荐监听** [D08:L59][D16:L189] |
| `window.on('windowStatusChange')` | 窗口模式（全屏/分屏/悬浮窗/自由多窗）变化 [D16:L96-116] |
| `window.on('windowRectChange')` | 窗口坐标或宽高变化 |
| `window.on('avoidAreaChange')` | 避让区（状态栏/导航条/软键盘/智慧多窗顶部横条）变化 [D16:L184][D05:L90-120] |
| `window.on('displayIdChange')` | 窗口移动到其他屏幕 |
| `display.on('foldStatusChange')` | 折叠状态（折叠/展开/悬停）变化——**不用于布局** [D08:L61-63] |
| `display.on('foldDisplayModeChange')` | 屏幕显示模式（主屏/子屏/全屏/双屏）变化 [D16:L182] |
| `display.on('change')` | 屏幕方向变化（窗口尺寸不变时也需它兜底，见下） |

### 6.3 时序坑（官方原文）
1. **窗口模式变化时，系统内窗口尺寸还未刷新**——要在 `windowStatusChange` 回调里拿新尺寸会拿到旧值；**新尺寸必须去 `on('windowSizeChange')` 回调里取**。[D16:L116]
2. **旋转 180° 等窗口大小不变的变化不会触发 `windowSizeChange`**，此时需监听 `display.on('change')` 感知屏幕方向变化。[D16:L160]
3. **折叠开合的触发时序**（双折叠）[D08:L65-66]：
   - 展开态→折叠态：`foldStatusChange(悬停态)` → `foldStatusChange(折叠态)` → `foldDisplayModeChange` → `windowSizeChange`
   - 折叠态→展开态：`foldStatusChange(悬停态)` → `foldDisplayModeChange` → `windowSizeChange` → `foldStatusChange(展开态)`
   - 结论：**页面布局的开合连续必须用断点 + `windowSizeChange` 实现**；「不推荐使用折叠状态监听接口实现页面布局的响应式布局和接续，避免在窗口变化但折叠状态未改变的场景下布局未能及时调整，出现页面异常。」[D08:L59-63]
4. **折叠开合过程中，窗口尺寸和断点的刷新建议只监听 `window.on('windowSizeChange')`**；不要在屏幕状态回调里主动去查 rect / displayId / avoidArea / density，换用对应的信息变化监听接口；**「不要默认在接口 A 中查询到的接口 B 中的数据始终是正确的」**（例：不要在 `windowRectChange` 回调里调 `getWindowAvoidArea`，改用 `on('avoidAreaChange')`）。[D16:L189-191]
5. **布局数据相关的回调里只做 UI 刷新逻辑，不要做 IO 等耗时逻辑**。[D16:L192]
6. **`aboutToAppear` 阶段拿不到正确的窗口尺寸**（此时窗口未必可见），应改在 `onPageShow` 获取；且 `windowRect` 是小窗缩放前的实际尺寸。[D16:L133-134]
7. **`window.getLastWindow()` 有查找延迟**，可能出现已横竖屏切换而状态栏还没切的情况；推荐用 `windowStage.getMainWindowSync()`（同步）。[D17:L1225-1228]
8. **`display` 接口规则不够清晰**：竖屏时进入任务中心（横屏应用）后 `onPageShow` 拿到的 display 信息不符合预期，建议改用 `window.getWindowProperties()`。[D17:L1250-1252]
9. **左右分屏 / 上下分屏**：上下分屏时窗口高度缩到约 1/2 或 1/3、宽度不变，垂直内容会被截断；官方方案是把页面放进 `Scroll` 并注意 `scrollBar`。[D16:L164][K01]
10. **折叠开合后阅读焦点不偏移**：`List` 用 `onScrollIndex` + `scroller.scrollToIndex()`；`WaterFlow` 若列数变化则改用 `WaterFlowLayoutMode.SLIDING_WINDOW`；`Scroll` 只能用 `scrollBy()` 自行计算距离。[D08:L98-171]
11. **横竖屏切换性能**：用 `@Component({ freezeWhenInactive: true })` 冻结不需要重排的子树；图片加 `autoResize(true)`；排查冗余 `onAreaChange`、`blur`、`linearGradient`。[D17:L850-891]

### 6.4 窗口旋转策略（多端要区别对待时）
- 18 种 `window.Orientation`：固定方向（PORTRAIT / LANDSCAPE / … / LOCKED）、自动旋转（AUTO_ROTATION 系列，含 `_RESTRICTED` 受控制中心开关约束）、带首选方向（USER_ROTATION_*）、跟随桌面（`FOLLOW_DESKTOP`）。[D17:L52-151]
- 三级配置：**应用级**（`module.json5 > abilities > orientation`）、**窗口级**（`setPreferredOrientation`，API 9+，Navigation/Router 都生效）、**页面级**（`NavDestination.preferredOrientation`，API 19+，仅 Navigation）。[D17:L407-506]
- 官方推荐：直板机 + 折叠态为竖屏、平板或展开态可旋转 → 配 `FOLLOW_DESKTOP`（避免在 Ability 生命周期里 `setPreferredOrientation` 造成启动时旋转动画）。[D17:L438][D17:L674]
- **电脑（2in1）无法由应用配置窗口旋转策略**。[D17:L672]

## 七、官方的布局设计原则（原文要点）

1. **适配的本质是适配窗口**：「无论是手机、折叠屏、平板还是电脑，其屏幕差异最终都体现为应用显示窗口宽高、比例的差异……通过一次性基于断点的布局适配，即可支持分屏、悬浮窗、自由窗口等多种窗口模式，确保界面在不同形态间平滑、连续地响应变化。」[D08:L18]
2. **断点设计两原则**：「① 两个宽度相近的窗口，页面布局相同，断点归一。② 高度相对宽度较小的窗口，呈现横向窗口或类方形窗口时，页面布局进行差异化设计，增加断点。」[D12:L32-42]
3. **断点面向窗口而非设备类型**。[D12:L68]
4. **断点不是越多越好**：「断点并非越多越好，通常每个断点都需要开发者'精心适配'以达到最佳显示效果。」[D12:L649]
5. **两级分工**：「自适应布局多用于解决页面各区域内的布局差异，响应式布局多用于解决页面各区域间的布局差异。」[D10:L10]
6. **响应式布局样式有明确适用阈值**：分栏 ≥600vp；重复用于内容放大超原图 150%；挪移用于宽高比变化 >200%；缩进用于纯文本/卡片，8/12 列下用 6/8 列缩进。[D12:L1140-1166]
7. **预定义差异参数 + 跨断点重算**：响应式组件体系「为不同窗口尺寸区间预定义差异化的布局参数（如 columns/span）和样式表现（如字体大小/边距）」，跨断点时触发重算。[D14:L5]
8. **监听纪律**：布局只监听 `windowSizeChange`；每种监听只处理自己返回的数据；布局回调只做 UI 刷新（详见 6.3 第 4/5 条）。[D16:L189-192]
9. **折叠适配三条硬要求**：展开态不应出现页面跳转/步骤增加/操作更复杂；不应破坏原有沉浸式体验或强制分屏；开合切换需保证任务连续性（状态能保存延续或快速恢复，不闪退不重启）。[D07:L178]
10. **不推荐用折叠状态监听做布局**（原文见 6.3 第 3 条）。[D08:L63]
11. **关闭复杂性优先**：设备泛类相同优先复用代码/共用 HAP；跨泛类或页面复杂度过高时，单独设计 UX + 单独 HAP 或用 if-else 断点实现第二套布局。[D07:L266-270][D09:L42][D07:L44-46]
12. **内容重要性决定单栏时展示谁**：三分栏在单栏状态下应展示哪一栏由内容优先级决定（邮箱优先内容区、日历优先导航区）。[D15:L347][D15:L411-413]
13. **小屏要保证内容完整可见**：小方形屏用 `Scroll` 支持滑动、弹窗用 `constraintSize({maxHeight:'90%'})` 防截断；圆形屏专用弧形组件并单独 HAP。[D13:L418-420][D13:L499-518][D13:L710]
14. **大屏要把底部导航改为侧边导航**：≥840vp（lg）用侧边导航（`Tabs.vertical`），≥1440vp（xl）用侧边分级导航（`SideBarContainer`）。[D13:L50][D13:L108]
15. **减少布局节点**：移除冗余节点、扁平化、优先 `@Builder` 代替无状态自定义组件、删除无用 Stack/Column/Row 嵌套。[D45:L3-22][D27]

### 8.2 FAQ / 最佳实践中点名的多端布局错误

## 九、对 Weaver 的具体建议（现状 → 建议 → 理由 → 迁移代价）

### 9.2 明确回答：**不该把三栏外壳整体改用官方栅格系统**

理由（按重要性排序）：
1. **官方压根没把「三栏」交给栅格。** 官方两张对照表里，「三分栏」的实现方案是 `SideBarContainer + Navigation + 断点`；`GridRow/GridCol` 只对应「挪移布局（图文组合）」和「缩进布局（单列列表）」。[D14:L9-20][D15:L9-20][D15:L288-334] 换句话说，Weaver 用 GridRow 重写三栏 = 逆着官方推荐走。
2. **语义不符。** 栅格的列宽是系统根据 columns/gutter 均分算出来的，**不允许开发者手配**；而 Weaver 的侧栏宽度是设计上固定的（`230` / `WeaverSpacing.LIST_W`），主区是弹性的。[D12:L596] 要在栅格里表达这件事，只能把侧栏列数按断点反复换算，既绕又脆。
3. **现方案本身就是官方认可的自适应手段。** 「固定宽度子组件 + `layoutWeight(1)` 弹性子组件」正是官方的**占比能力**（`layoutWeight` 在父容器为 Row/Column/Flex 时生效），[D11:L252-273] 已经天然覆盖了窗口缩放、分屏、悬浮窗三种形态，没有已知性能问题。
4. **会撞上 CodeLinter 硬规则。** 三栏里如果出现「GridCol 的 span 恒等于 columns」的写法（固定栏最容易写成这样），直接命中 `grid-columns-span` 反例。[D27]

**所以该改的是另外三件事**（见 9.3 A/B/C），而不是重写布局。

### 9.3 建议动作清单（按优先级）

**A. 断点来源换成官方 API（强烈建议，1 天）**
- 现状 → 建议：`AppShell.setupBreakpoint()` 不再自己 `matchMediaSync`；改为在 `loadContent` 回调后调一次 `getUIContext().getWindowWidthBreakpoint()` 取初值，并注册 `mainWindow.on('windowSizeChange')`，回调中重新取断点写 `AppStorage`；UI 侧沿用现有 `@StorageLink`/`app.ui.breakPoint` 消费方式。[D12:L107-220][D16:L136-158][D08:L89-96]
- 理由：① 官方断点阈值「个别设备由系统产品化配置调整」，自己写死 600/840 会漂移 [D24:L1646]；② `mediaquery` 走的是「应用页面可绘制区域宽度」，与窗口断点枚举的口径不必完全一致；③ 一条 `windowSizeChange` 同时覆盖分屏、悬浮窗、自由窗口、折叠开合四种变化 [D08:L18][D08:L59]。
- 映射：`WIDTH_XS|WIDTH_SM → BreakPoint.SM`、`WIDTH_MD → BreakPoint.MD`、`WIDTH_LG|WIDTH_XL → BreakPoint.LG`（保留现有枚举，改动面最小；顺带获得 xl 的区分能力）。
- 代价/风险：低。注意首帧必须在 `loadContent` 之后取断点（`aboutToAppear` 阶段拿到的窗口信息可能不准 [D16:L133]）；`windowSizeChange` 与媒体查询回调的触发时机不同，需回归一次「冷启动 → 设备旋转 → 分屏 → 折叠开合」四种场景。
- 备注：`@Env(SystemProperties.BREAK_POINT)`（API 22+）在 API 23 上可用，`AppShell` 已是 `@ComponentV2`，是更「声明式」的替代方案，但会把断点消费方式从 `@StorageLink` 改成 `@Env`，改动面更大，不建议与 A 同批做。[D25:L5,L289]

**B. 去掉布局分支里的设备类型判据（建议，0.5 天）**
- 现状 → 建议：`deviceInfo.deviceType === '2in1'` 仍可用于 **PC 专有外壳**（`PcWindowBar`、标题栏避让、窗口控制条），但**不能作为布局分支的开关**；`isPc` 涉及布局的地方改由断点决定。[D26]
- 理由：`one-multi-breakpoint-check` 明文「一多特性必须使用系统断点判断是否开启，不能通过设备类型、设备方向或是否可折叠等属性来判断」。[D26] 官方区分设备的办法也是「参考常用设备断点区间表」，而不是 `deviceType`。[D12:L1235-1241]
- 代价/风险：低-中。需要复核 `AppShell.wideLayout:358`（PC 才插 `PcWindowBar`）以及 PC 窗口被拖到 md 断点时的呈现——**这属于产品决策，需要你拍板**：PC 窗口缩窄到 md 时，是保留窗口控制条（则 pc 外壳与断点解耦），还是退回平板的嵌入侧栏（则纯断点驱动）。

**C. 启用 `@cross-device-app-dev` 规则集（建议，1 小时）**
- 建议在 `code-linter.json5` 的 `ruleSet` 增加 `"plugin:@cross-device-app-dev/recommended"`。[D26-D33]
- 理由：这是官方把「一多常见错误」固化成可自动检查的清单（设备类型判据、缺 `windowSizeChange` 监听、栅格误用、px 单位、fp 单位、Tabs 侧边导航）。[D26-D33]
- 代价/风险：低，但会一次性冒出一批告警（预计集中在 `size-unit` 的数值宽高与 `one-multi-breakpoint-check`）。可以先用 `"warn"` 收敛，不必一次清零。

**D. 可选：中心编辑区加「缩进布局」（可选，0.5 天）**
- 建议：把 `EditorPane` 外层包一层 `GridRow({ columns: { sm:4, md:8, lg:12 } })` + `GridCol({ span: { sm:4, md:6, lg:8 }, offset: { sm:0, md:1, lg:2 } })`，宽屏正文居中留白。[D15:L661-676][D12:L1166]
- 理由：这是栅格对 Weaver 唯一高收益的场景——写作编辑器在 12 列宽屏上正文行宽过长，官方缩进布局就是为此设计的；实现是纯样式包裹，不动任何业务状态。
- 代价/风险：极低。注意 `span` 不要等于 `columns`（否则命中 `grid-columns-span`），`span/offset` 不要用小数。[D27][D28]

**E. 可选：多端资源限定词目录（按需，1 天）**
- 建议：建 `entry/src/main/resources/tablet/element/float.json`、`.../2in1/element/float.json`，把**确实要分端**的量下沉为资源：侧栏宽度、列表栏宽度、页面外边距、正文字号上限。base 必须保留同名的默认值。[D18:L34,L70-101][D06:L83-105]
- 理由：`UiStore.isTablet ? 230 : LIST_W` 这类三目表达式会随设备增多而爆炸；官方做法是同一 `$r('app.float.xxx')` 在不同限定词目录取不同值。
- 代价/风险：中。`DesignTokens.ets` 是集中式常量表，下沉后调用点要改为 `$r(...)`，改动面较广；建议只搬「设计上确实分端」的少量 token，不要一次全搬。

**F. 暂缓：用 `SideBarContainer + Navigation` 重写三栏**
- 只在出现以下**明确需求**时才做：小窗/窄断点下侧栏需要 `Overlay` 覆盖式弹出、用户拖拽调整侧栏宽度、内置折叠按钮、或列表↔详情需要分栏路由联动。[D14:L83-111][D15:L165-230]
- 代价：中-高（1–3 人日）。`SideBarContainer` 只接受两个子组件（侧栏、内容），需把「文稿列表 + 中心区」封装为内容子组件；官方 sm/md/lg 下侧栏宽度 `80% / 50% / 40%`（或三分栏场景 `80% / 50% / 20%`）可直接套用。[D15:L173][D15:L202][D15:L296]
- **关于 `Navigation` 的历史教训要修正认知**：`pages/Index.ets:3-9` 记录的两个坑——「`mode` 默认 `Auto` 自动分栏」「`hideNavBar(true)` 把内容区一起藏」——都是**使用了默认值**造成的。官方写法是显式 `.mode(NavigationMode.Stack | Split)`（`Auto` 本身就是「基于组件宽度自适应单栏和双栏」）[D04:L9]，并按断点用 `getNavMode()` 显式切换 [D15:L280-285]。若将来引入，务必显式指定 `mode`，不要依赖默认。
- 风险：现在 `Route` 是「外壳之上的全屏覆盖」，改成分栏路由会牵动全部 `pages/dest/*`，属于结构性改动。

**G. 明确用不了的能力**
- `ContainerReader`（容器级断点，适合「侧栏拖窄后主区自己换布局」）**从 API 26.0.0 起才支持**，Weaver 的 `compatibleSdkVersion = 6.1.0(23)`，**用不了**。[D02:L3] 替代：在 `windowSizeChange` 里用 `窗口宽度 − 侧栏宽度` 手算可用宽度再判断点。
- 断点阈值**没有系统资源形式**（无 `$r('sys.float.breakpoint_*')`），不要去找。

### 9.4 一句话结论
> **保留现有三栏布局（这是官方认可的「占比能力」用法），把断点从「自己写的 mediaquery」换成「系统断点 API（`getWindowWidthBreakpoint` + `windowSizeChange`）」，把设备类型判据从布局分支里剔除，启用 `@cross-device-app-dev` 规则集，并在中心编辑区用一次官方「缩进布局」。不要为了「用上官方栅格」而重写外壳。**

### 9.5 文档中未找到的事项（如实说明）
- 官方**未给出**三栏工作台中「侧栏 / 列表栏 / 主内容区」的固定宽度推荐值；只有按断点给出的示例百分比（侧栏 80%/50%/40%、三分栏 80%/50%/20%、`navBarWidth` 50%/40%/30%）。[D15:L173][D15:L202][D15:L296][D15:L326]
- 官方**未提供**「主区最小宽度」的通用断点公式；只有组件级接口 `Navigation.minContentWidth`。[D04:L51-53]
- 官方**未提供**「用资源限定词表达断点阈值」的方案（断点阈值不通过 `$r` 暴露）。
- 「固定宽度侧栏 + 弹性主区」这一具体组合，文档中**没有单独的正/反例**；判定依据是从「占比能力属于自适应布局」与「三分栏归 SideBarContainer+Navigation」两处推导的。[D11:L252-273][D14:L15-17]
