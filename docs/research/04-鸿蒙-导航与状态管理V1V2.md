## 一、结论摘要（可直接执行）

1. **官方明确推荐 Navigation**："因此，推荐使用组件导航（Navigation）来实现页面跳转以及组件内的跳转，以获得更佳的使用体验。"（`arkts-navigation-introduction`）；`@ohos.router` 的文档标题直接带"**（不推荐）**"（`js-apis-router`、`arkts-routing`）。
2. **Navigation 的 `mode` 默认值是 `NavigationMode.Auto`**，官方定义："默认值：NavigationMode.Auto 自适应：基于组件宽度自适应单栏和双栏。"（`ts-basic-components-navigation`）→ 凡是自绘响应式外壳，**必须显式写死 mode**，不能吃默认值。
3. **`hideNavBar(true)` 隐藏的是整个"导航页"**："设置为 true 时，隐藏 Navigation 的导航页，包括标题栏、内容区和工具栏。如果此时路由栈中存在 NavDestination 页面，则直接显示栈顶 NavDestination 页面，反之显示空白。"（`ts-basic-components-navigation` / `faqs-arkui-1018`）→ 我们踩的"整屏空白"是**用法错误**，不是 Navigation 的缺陷：我们把主界面放在了被隐藏的那一半里。
4. **官方对"侧栏 + 列表 + 主内容"三栏工作台有明确方案**：`SideBarContainer`（最左栏）+ `Navigation` 的 Split 分栏（列表 = NavBar，主内容 = NavDestination），mode / navBarWidth 按断点显式赋值（`bpta-multi-device-page-layout` 的"三分栏""三分栏典型场景——邮箱"）。
5. **官方对"不使用 Navigation、改用自定义状态切换"没有任何条文**——文档中未找到明确的禁止，也未找到明确的推荐示例。我们的做法属于**文档未覆盖的自定义方案**，不是官方路径。
6. **代价是实打实的功能缺失，且已经发生**：`onBackPress` 是 `@Entry` 组件级的返回键/侧滑回调（`faqs-arkui-531`），Navigation 体系里由 `NavDestination.onBackPressed` 接管（`ts-basic-components-navdestination`）。我们的外壳没有接任何返回处理 → **二级覆盖页上按返回键会直接退出应用，而不是关闭覆盖页**。这是当前唯一"必须马上补"的缺口。
7. **`@Builder` 默认按值传递**："调用 @Builder 装饰的函数默认按值传递。当传递的参数为状态变量时，状态变量的改变不会引起 @Builder 函数内的 UI 刷新。"按引用只在"**仅一个参数**且该参数**直接传入对象字面量**"时生效（`arkts-builder`）。
8. **`$$` 不是语法**：文档明说"这里 `$$` 不是必须的参数形式，可以换成其他名称"（`arkts-builder`）——它就是个形参名。
9. **V1→V2 核心映射**：`@State`→`@Local`（需外部初始化时用 `@Param`+`@Once`）；`@Prop`→`@Param`；`@Link`→`@Param`+`@Event`；`@Observed`/`@ObjectLink`/`@Track`→`@ObservedV2`/`@Trace`；`@Watch`→`@Monitor`；`@Provide`/`@Consume`→`@Provider`/`@Consumer`；V1 无计算属性 → `@Computed`（`arkts-v1-v2-migration`）。
10. **V2 的本质改进是"数据本身可观察"**：V1 的四个硬伤（状态变量不能独立于 UI 存在、只能感知第一层、冗余更新、装饰器配合限制多）在 V2 被逐条解决（`arkts-v1-v2-update-difference`）。
11. **`@Trace` 对数组的观测边界**：只有 `push/pop/shift/unshift/splice/copyWithin/fill/reverse/sort` 这些 API 调用会被观测；**不支持观察 Function 类型**；未 `@Trace` 的属性用在 UI 上不刷新（`arkts-new-observedv2-and-trace`）。
12. **API 19+ 混用放宽但三条硬禁令仍在**：① V1 装饰器不能和 `@ObservedV2` 一起用；② V2→V1 时 V1 不支持用装饰器接收 `@ObservedV2` 装饰的 class（编译报错）；③ V1 中 `@Link` 只能被 V1 状态变量初始化（`arkts-v1-v2-mixusage`）。另：**`Repeat` 懒加载模式不支持与状态管理 V1 配合使用**（`arkts-new-rendering-control-repeat`）。

### 2.3 官方"为什么"（`arkts-navigation-introduction` 原文，Navigation 架构优势 6 条）

1. 接口上显式区分标题栏、内容区和工具栏，实现更加灵活的管理和 UX 动效能力；
2. 显式提供路由容器概念，由开发者决定路由容器的位置，支持在全模态、半模态、弹窗中显示；
3. **整合 UX 设计和一次开发多端部署能力，默认提供统一的标题显示、页面切换和单双栏适配能力**；
4. 基于通用 UIBuilder 能力，由开发者决定页面别名和页面 UI 对应关系，提供更加灵活的页面配置能力；
5. 基于组件属性动效和共享元素动效能力，将页面切换动效转换为组件属性动效实现，提供更加丰富和灵活的切换动效；
6. 开放了页面栈对象，开发者可以继承，能更好的管理页面显示。

> 第 3 条正是我们冲突的来源：**单双栏适配是"默认"给的**，而我们要自己控制，于是要么关掉它（显式 mode），要么不要它。

### 2.4 官方对"少数几个全屏二级页"给了什么路径？

- **给了，但都是 Navigation 内部的解法**，不是"改用状态切换"：
  - `faqs-arkui-1018` 场景一/二：`hideNavBar(true)` + 在 `aboutToAppear` 里 push 一个子页当主页 + `setInterception`（当 `to == 'navBar'` 时重新 push 主页）。
  - `faqs-arkui-1094`（Navigation 加载启动页方案）给了三套方案，同样全部基于 Navigation 或 Router：
    - 方案一：隐藏导航页 + 路由拦截；
    - 方案二：闪屏页做成 NavDestination，定时 `pop` 销毁；
    - 方案三：Router 页面做闪屏页，主页交给 Navigation，`onPageShow` 里 `router.clear()`。
  - 该 FAQ 还给了官方自己的横评结论：**"方案一：平板分栏模式下左侧闪屏页、右侧空白。方案二：平板分栏模式下左侧主页、右侧闪屏页。方案三：不受平板分栏的影响。"** —— 官方承认分栏模式会让"单栏思维"的做法翻车。
- **"用状态切换代替路由"的官方示例或最佳实践：文档中未找到。**

## 三、Navigation 属性语义表

**枚举定义（`ts-basic-components-navigation`）**

| `NavigationMode` | 值 | 说明原文 |
| --- | --- | --- |
| Stack | 0 | "导航页与内容区独立显示，相当于两个页面。" |
| Split | 1 | "导航页与内容区分两栏显示。"（含 6 条细则，见下） |
| Auto | 2 | "API version 9 及之前版本，Navigation 宽度 >=520vp 时，采用 Split 模式显示；Navigation 宽度 <520vp 时，采用 Stack 模式显示。**从 API version 10 开始：Navigation 宽度 >=600vp 时，采用 Split 模式显示；Navigation 宽度 <600vp 时，采用 Stack 模式显示**，600vp 等于 minNavBarWidth(240vp) + minContentWidth (360vp)。" |
| AUTO_WITH_ASPECT_RATIO | 3 | "Navigation 宽度>=600vp 且高宽比小于等于 1.2 时，采用 Split 模式显示；否则采用 Stack 模式显示。"（API 24+） |

Split 模式官方 6 条细则（原文摘要）：① navBarWidth 最终取值参见表 1；② 缩小组件尺寸时，**先缩小内容区至 minContentWidth，再缩小导航页至 minNavBarWidth**，若继续缩小，先缩小内容区，内容区消失后再缩小导航页；③ 导航页设为固定尺寸时，持续缩小则导航页最后压缩显示；④ 只设置了 navBarWidth 则分割线不可拖动；⑤ 分割线热区左右各 2vp，**建议避让 4vp 以上**；⑥ **"Split 模式下，内容区若只存在一个页面，则页面左上角不会显示返回按钮。"**

## 四、NavPathStack 与二级页面返回

### 4.1 NavPathStack 接口清单（`ts-basic-components-navigation` + `arkts-navigation-jump`）

| 分类 | 接口 | 说明（摘） |
| --- | --- | --- |
| 跳转 | `pushPath(info, animated?)` / `pushPath(info, options?)` | "将 info 指定的 NavDestination 页面信息入栈。" 第二形态按 `NavigationOptions.LaunchMode` 行为不同（API 12+） |
| | `pushPathByName(name, param, animated?)` | "将 name 指定的 NavDestination 页面信息入栈，传递的数据为 param。" |

| 删除 | `removeByIndexes` / `removeByName` / `removeByNavDestinationId` | 删除栈中特定页面（Router 不支持） |
| 移动 | `moveToTop(name)` / `moveIndexToTop(index)` | 移到栈顶 |
| 参数获取 | `getParamByIndex(index)` / `getParamByName(name): Array<unknown>` / `getIndexByName(name): Array<number>` / `getAllPathName()` / `getPathStack(): Array<NavPathInfo>`（API 19+） | `getParamByName` 返回**数组**（同名页面可能多个） |

**导航控制器获取方式（官方两种，`arkts-navigation-jump`）**：
- 方式一：`AppStorage.setOrCreate<NavPathStack>('basicNavigationStack', this.navStack)` + 子页 `AppStorage.get`；
- 方式二：`NavDestination.onReady((ctx: NavDestinationContext) => { this.navPathStack = ctx.pathStack; })`。
- 架构文档补充："也可以全局维护一个单例的 NavPathStack，在任意地方获取并执行路由操作（注意：页面切换动画和布局必须在 UI 线程中才可以生效，依赖 Vsync 信号）。"
- **限制**：`arkts-navigation-jump` 明列 4 条，其中三条与我们相关：
  1. "NavPathStack 对象和 Navigation 需要一一对应，**不可复用**。"
  2. "NavPathStack 主要控制的是 NavDestination 页面跳转、删除等，**无法直接操作 NavBar 导航栏，若想跳转到 NavBar 页面只能通过 clear 清空路由栈的方式**。" ← **这条就是"为什么 pop 到最后回到了导航页，而不是退出页面"的根因。**
  3. "不建议开发者通过监听生命周期的方式管理自己的路由栈，可通过 NavPathStack.getPathStack 查询路由栈。"
  4. "在应用处于后台状态下，调用 NavPathStack 的栈操作方法，会在应用再次回到前台状态时触发刷新。"
- API 参考里还有一条易踩的缓存语义："连续调用多个导航控制器方法时，**中间被 pop 的页面会被缓存，后续 push 同名页面时会优先复用该页面，不会走新的页面创建流程**。"（`pop` 小节）
- 性能/正确性警告（`updateTransition` 小节内嵌）："**不建议在 aboutToAppear 中使用栈操作，此时的页面还未构建完成，会导致白屏或跳转失败等问题。**"（注意：`faqs-arkui-1018`/`faqs-arkui-1276` 的官方示例恰恰在 `aboutToAppear` 里 push 默认页——两条指导存在张力，实践中建议放到 `onAppear` 或用 `setTimeout(…, 0)` 错帧。）

### 4.2 跳转传参与取参（`arkts-navigation-split-mode` 完整示例）

```
// 子页：onReady 里取 param
NavDestination() { /* ... */ }
  .onReady((ctx: NavDestinationContext) => {
    let param = ctx.pathInfo.param as NewsItem;   // 官方写法
    this.title = param?.title;
  })
```

- 返回传参：`NavDestination.onResult((param: Object) => {...})`（API 15+）；`arkts-navigation-jump` 明确"自 API15 起，推荐开发者使用 onResult 处理返回场景的路由参数"。
- 也可主动查询：`getParamByName('pageOne')` 等（注意返回数组）。

### 4.3 路由拦截 `setInterception`（`ts-basic-components-navigation` API 12+）

`NavigationInterception` 成员：

| 成员 | 说明原文 | 关键差异 |
| --- | --- | --- |
| `willShow: InterceptionShowCallback` | "页面跳转前的回调，允许操作栈，在当前跳转中生效。**拦截的页面会被创建**。" | 会先创建再销毁，有开销 |
| `didShow: InterceptionShowCallback` | "页面跳转后回调。在该回调中操作栈在**下一次跳转中刷新**。" | 不能拦当次 |
| `modeChange: InterceptionModeCallback` | "Navigation 单双栏显示状态发生变更时触发该回调。" | 断点切换可见 |
| `interception: InterceptionCallback`（API 22+） | "页面跳转前的回调，允许操作栈，在当前跳转中生效。**拦截的页面不会被创建**。" | 更早、更省 |

`InterceptionShowCallback = (from: NavDestinationContext | NavBar, to: NavDestinationContext | NavBar, operation: NavigationOperation, isAnimated: boolean) => void`——**`from`/`to` 为字符串 `navBar` 时表示 Navigation 首页**。

`arkts-navigation-jump` 的两条硬约束：
- "无论是哪个回调，**在进入回调时路由栈都已经发生了变化**。"
- "interception 回调时机比 willShow 更早，也可以做拦截重定向的能力，区别是，前者触发时不会创建被拦截的页面，willShow 触发时会创建被拦截的页面然后销毁。"

### 4.4 返回：官方推荐做法 & 我们踩过的坑

**坑：`pop` / 返回键回到导航页而不是退出页面。** 官方 FAQ 原文（`faqs-arkui-430`）：

> "因为 Navigation 隐藏导航栏的属性 **hideNavBar 默认值为 false**，调用路由栈的 pop 时均会返回到导航栏 NavBar，由于 hideNavBar 默认 false，当调用 pop() 时系统会**优先显示 Navigation 组件自带的导航栏，而非完全退出页面栈**。"
> 解决措施：① `hideNavBar(true)`；② "使用 `onBackPressed()` 方法重写返回键逻辑，通过 `router.back()` 退出 Navigation 所在的页面。"

**官方返回体系（三层）**

| 层级 | 手段 | 适用范围（原文） |
| --- | --- | --- |
| `@Entry` 页面级 | `onBackPress(): boolean` | `faqs-arkui-531`："属于自定义组件的生命周期回调函数之一，**当用户点击返回按钮或侧滑返回时触发，仅 @Entry 装饰的自定义组件生效**。返回 true 表示页面自己处理返回逻辑，不进行页面路由；返回 false 表示使用默认的路由返回逻辑，不设置返回值按照 false 处理。" 也见 `faqs-arkui-273`："生命周期函数 onBackPress **只能在 @Entry 组件中使用**。" |
| NavDestination 级 | `onBackPressed(callback: () => boolean)` | `ts-basic-components-navdestination`："**当与 Navigation 绑定的导航控制器中存在内容时，此回调生效**。当点击返回键时，触发该回调。返回值为 true 时，表示重写返回键逻辑，返回值为 false 时，表示回退到上一个页面。" `faqs-arkui-1117`："该方案支持拦截**系统侧滑**及 NavDestination 标题栏的返回事件，**但不支持拦截 `NavPathStack.pop()` 操作**。" |
| 路由栈级 | `popToName` / `popToIndex` / `popToIndex(0)` | "返回到索引为 0 的页面" / "返回到根首页（清除栈中所有页面）" |

**跨级返回不触发中间页生命周期**（`faqs-arkui-418`，回答我们"会不会触发 onPop"这类疑问）：

> "仅按 push 的反序返回时会触发 onPop。以 A->B->C->D 为例，仅如下的 pop 操作会触发对应页面的 onPop 回调：D->C，C->B，B->A，**popToName 属于跨级返回，会跳过中间页面栈而不触发其生命周期回调**，这与逐级 pop 的机制不同。"
> "自 API15 起，推荐开发者使用 onResult 处理返回场景的路由参数。"

**侧滑手势的两种官方拦截方式**（`faqs-arkui-531`）：
- 方案一：`UIContext.getPromptAction()` 的 `onWillDismiss`（判断 `DismissReason.PRESS_BACK` / `DismissReason.SLIDE`）；
- 方案二：Navigation 自定义弹窗（`NavDestinationMode.DIALOG`）+ `onBackPressed`。
- 且该 FAQ 明确警告：**误拦截会导致"侧滑无法从首页退出应用"**，排查日志关键字 `router user onBackPress return true`、`router consumed backpressed event`、`禁止手势返回`。

## 五、Navigation 白屏/异常已知原因清单

### 5.1 `faqs-arkui-1018`（官方五场景，最权威）

| 场景 | 官方定位 |
| --- | --- |
| 一：打开应用并加载 Navigation 页面时白屏 | **"排查是否设置了 Navigation 的 hideNavBar 属性为 true。设置为 true 时，隐藏 Navigation 的导航页，包括标题栏、内容区和工具栏。如果此时路由栈中存在 NavDestination 页面，则直接显示栈顶 NavDestination 页面，反之显示空白。"** 解法：① `hideNavBar` 置 false；② 在 `aboutToAppear` 中 push 子页 + `setInterception`，当 `to == 'navBar'` 时重新 push |
| 二：执行 pop 或 clear 返回操作时白屏 | 同上（同一根因） |
| 三：点击跳转后目标页面白屏 | 排查路由表配置 |
| 四：平板分栏模式下点左侧导航后右侧白屏 | 排查路由表配置 |
| 五：预览器调试时子页白屏 | **"预览器不支持 Navigation 路由跳转，建议使用模拟器或真机进行调试。"** |

路由表校验清单（场景三/四，逐字）：
- 系统路由表：① 检查 entry 模块 `src/main/module.json5` 是否引用 `"routerMap": "$profile:route_map"`；② 检查 `pushPath` 入参页面名称与 `route_map.json` 中 name 一致，"**特别注意大小写**"；③ "检查子页面的根节点是否使用 NavDestination 包裹"。
- 自定义路由表：① 检查是否使用 `navDestination` 注册路由表；② 名称大小写；③ "**检查自定义路由表的函数是否用 @Builder 装饰**"；④ 根节点是否 NavDestination。
- 另：场景一的官方示例里有一行注释值得注意：`this.pathStack.pushPathByName('NavDesOne', undefined, false); // 注意关闭转场动画效果`。

### 5.2 `faqs-arkui-390`（"可能原因是什么"）

1. 跨模块跳转配置错误：路由表页面"需要配置入口函数 Builder，并且需要使用 NavDestination 组件才能展示页面"；"HAR/HSP 模块可以跳转，可以通过 module.json5 文件查看 type 类型是否为 'har' 或者 'shared'，**如果是 feature 则会出现错误**"；"即使配置正确，跳转时仍可能出现白屏。可以尝试**清理项目**，以恢复正常跳转。"
2. **NavBar 处于隐藏状态**："当设置为 true 时，NavBar 会被隐藏。如果此时页面栈为空，页面表现上会处于白屏。"
3. 使用的是 Previewer 调试："Previewer 不支持系统路由表跳转。"
4. 其他："**跳转的 Name 为空或者不存在时，会跳转白屏。**"

### 5.3 `faqs-arkui-415`（pushPathByName 空白）六条原因

1. 路由未正确配置（未配系统路由表 / 未设 `navDestination` / 目标页未注册 / builder 未定义）；
2. 模块类型错误（`type` 应为 `har`/`shared`，避免 `feature`）；
3. **NavBar 隐藏导致页面栈异常**；
4. 跳转名称无效或为空；
5. 调试环境不兼容（Previewer）；
6. **子页面错误创建导航栈**："子页面自行创建 NavPathStack 实例（如 `new NavPathStack()`），导致与父级 Navigation 路由栈冲突，**页面无法渲染**。" 解法：`@Consume('pageStack') pageStack: NavPathStack;`。

并且给出了接口层面的重要局限：

> "pushPathByName 是**同步方法**，跳转至不存在的页面时**不会抛出异常，直接显示空白页面**。"
> "推荐替代方案：改用 pushDestinationByName（异步方法），可捕捉错误并重定向。"

### 5.4 分栏空栈占位（`faqs-arkui-1276`）

- 现象："Navigation 在 Split 模式下，未点击左侧导航栏时，右侧子页显示区显示为空白。"
- 背景："该属性默认为 Auto 模式，在该模式下会自动监听屏幕属性，**当为折叠屏或平板时，默认分栏显示**，在折叠状态或普通手机时可为单栏显示。"
- 方案一：`aboutToAppear` 里 push 一个 `DefaultPage` 占位页；**该页必须重写 `onBackPressed`**——官方注释："返回 true 表示自定义返回，**能避免返回空白页面**。返回 false 则表示系统默认返回，会返回空白页面。"
- 方案二：API 20 的 `splitPlaceholder`。
- 补充 FAQ："API20 以下，当采用 Auto 模式时，如何判断是否需要推送默认显示页面？" → 用 `@ohos.deviceInfo` 的 `deviceType` + `@ohos.display` 的 `isFoldable`。**官方承认 Auto 模式下必须自己做设备判断**——这本身就是 Auto 不适合自绘外壳的旁证。

## 七、@Builder 参数传递规则（含正确写法与官方出处）

来源：`arkts-builder`（1882 行，含 8 个"常见问题"小节）。

### 7.1 规则原文（`arkts-builder`"参数传递规则"节，逐字）

> 自定义构建函数的参数传递有**按回调传递，按引用传递和按值传递**，均需遵守以下规则：
> - @Builder 装饰的函数参数类型**不允许为 undefined、null 和返回 undefined、null 的表达式**。
> - 在 @Builder 装饰的函数内部，**不允许改变参数值**。
> - @Builder 内 UI 语法遵循 UI 语法规则。
> - **按回调传递和按引用传递时，支持 @Builder 函数内 UI 组件刷新。按引用传递只在传入一个参数且该参数直接传入对象字面量时生效，有多个参数时不支持 @Builder 函数内 UI 组件刷新。**
> - 使用引用传递时，在 @Builder 函数中不能修改参数的属性，但使用 `UIUtils.makeBinding` 并传入写回调时，我们可以在 @Builder 函数内修改属性，并同步到调用 @Builder 的组件中。

### 7.2 三种方式的正确写法

**① 按值传递（默认，**不刷新**）**

```
@Builder
function overBuilderByValue(paramA1: string) {
  Row() { Text(`UseStateVarByValue: ${paramA1} `) }
}
// ...
overBuilderByValue(this.label)   // 状态变量改变，Text 不刷新
```

**② 按引用传递（唯一可用形态：**一个参数 + 直接传对象字面量**）**

```
class Tmp { public paramA1: string = ''; }

@Builder
function overBuilderByReference(params: Tmp) {
  Row() { Text(`UseStateVarByReference: ${params.paramA1} `) }
}
// ...
overBuilderByReference({ paramA1: this.label })   // ✅ 传入"对象字面量"，会刷新
```

**反例（两个参数，一定不刷新）**——官方标注"**使用了两个参数，用法错误**"：

```
@Builder
function overBuilder1(param: GlobalTmp1, num: number) { /* ... */ }
// ...
overBuilder1({ strValue: this.objParam.strValue }, this.num)      // ❌ 不刷新
overBuilder2({ strValue: ... }, { numValue: ... })                // ❌ 两个对象字面量也不刷新
```

**正例（合并为单一对象字面量）**：

```
@Builder
function overBuilder3(param: GlobalTmp3) {
  Column() { Text(`strValue: ${param.strValue}`); Text(`num: ${param.numValue}`) }
}
@State objParam: GlobalTmp3 = new GlobalTmp3();
// ...
overBuilder3({ strValue: this.objParam.strValue, numValue: this.objParam.numValue })  // ✅ 传一个参数，正确用法
```

**③ 按回调传递（API 20+，官方首选替代）**

```
import { Binding, MutableBinding, UIUtils } from '@kit.ArkUI';

@Builder
function customButton(num1: Binding<number>, num2: MutableBinding<number>) {
  Row() {
    Column() {
      Text(`number1: ${num1.value}, number2: ${num2.value}`)
      Button(`only change number2`).onClick(() => { num2.value += 1; })
    }
  }
}
// 调用处：
customButton(
  UIUtils.makeBinding<number>(() => this.number1),                                  // 只读，返回 Binding
  UIUtils.makeBinding<number>(() => this.number2, (val: number) => { this.number2 = val; })  // 可写，返回 MutableBinding
)
```
官方说明："使用 `UIUtils.makeBinding()` 包装读取状态变量的回调函数作为参数传入 @Builder 函数，可以支持 @Builder 函数中 UI 组件刷新。"

### 7.3 限制条件（`arkts-builder` 逐字 5 条）

1. 在没有使用 MutableBinding 时不允许修改参数值，修改不会触发 UI 刷新；**"若按引用传递参数且仅传入一个参数时，修改参数内部的属性会抛出运行时错误。"**
2. 按引用传递传入一个参数时，可以触发动态渲染 UI。
3. **"如果 @Builder 传入的参数是两个或两个以上，且未使用按回调传递参数，不会触发动态渲染 UI。"**
4. **"@Builder 传入的参数中同时包含按值传递和按引用传递，不会触发动态渲染 UI。"**
5. **"不允许在 @Builder 函数里修改参数的属性，否则会抛出运行时错误，从 API version 23 开始，将返回错误码 140109。"**

### 7.4 `$$` 的真实身份

`arkts-builder`"多层 @Builder 函数嵌套"节原文：

> "在 @Builder 函数内调用自定义组件或其他 @Builder 函数，实现多个 @Builder 嵌套使用。若要实现**最内层**的 @Builder 动态 UI 刷新功能，**每层调用 @Builder 的地方必须使用按引用传递的方式**。这里 **`$$` 不是必须的参数形式，可以换成其他名称**。"

即 `$$` 只是官方示例惯用的形参名（`function parentBuilder($$: ThisTmp)`），**不是新语法**。真正起作用的是"每层都传对象字面量、且只有一个参数"。

### 7.5 与我们真实故障直接对应的两条官方条目

**(a) `@Builder` 内的状态变量不刷新** —— 根因就是 §7.1 的按值传递规则。官方给的三条出路：改成"单参数对象字面量"、改成 `UIUtils.makeBinding`、或把变化部分改成在 `@Builder` 内部读 `this`（官方示例 `@Builder 支持状态变量刷新` 与 `在 @Builder 内创建自定义组件传递参数不刷新问题` 覆盖前者）。我们 `AppShell.ets` 的注释（"只传静态的枚举与文案，凡是随状态变化的东西一律在 @Builder 内部读 this/全局状态"）**与官方指导方向一致，是文档认可的做法**。

**(b) 把 `@Builder` 存进变量/数组后再在 UI 中使用会导致刷新时节点显示异常** —— `arkts-builder`"在 UI 语句外调用 @Builder 函数或方法影响节点正常刷新"节，原文：

> "当 **@Builder 方法赋值给变量或者数组后**，在 UI 方法中无法使用，且会造成**刷新时节点显示异常**。"

官方反例（正是"Builder 装进数组给 Swiper/Stack 之类用"的形态）：

```
private bgList: Array<CustomBuilder> = [this.myImages(), this.myImages2()]; // 错误用法，应避免在 UI 方法外调用 @Builder 方法
@State bgBuilder: CustomBuilder = this.myImages();                          // 错误用法
```
官方正例：**直接在 UI 语句中传/调**

```
Text('2').background(this.myImages)     // 直接传递 @Builder 方法
Text('3').background(this.myImages())   // 直接调用 @Builder 方法
```

> **说明（如实交代）**：我们记录的"`@Builder` 嵌在 `ForEach` 里再放进 `Swiper` 会导致重渲染后内容消失"这一具体组合，**文档中未找到逐字对应的条目**。最接近的是上面这一条（Builder 存变量/数组 → 刷新型显示异常）与 `faqs-arkui-619`（ForEach 非初次渲染时数据更改 UI 不刷新 / 删除项后重复显示）。**结论：该故障可归因于"Builder 未在 UI 语句内直接使用"+"ForEach key 生成规则不当"两类官方已承认的问题，但官方没有为这个具体组合出专条 FAQ。**

### 7.6 与 `Repeat` 混用时的额外要求

`arkts-new-rendering-control-repeat`"与 @Builder 混用时状态变量未刷新"节原文：

> "当 Repeat 与 @Builder 混用时，如果**只传递 RepeatItem.item 或 RepeatItem.index**，参数值的改变不会引起 @Builder 函数内的 UI 刷新。**推荐使用按引用传递，即将 RepeatItem 类型整体进行传参**，组件才能监听到数据变化。除此之外，从 API version 20 开始，开发者可以通过使用 `UIUtils.makeBinding()`…"

官方示例中的三行对照（同一 `Repeat` 内）：
```
this.buildItem1(UIUtils.makeBinding<number>(() => ri.item)) // ✅ 刷新
this.buildItem2(ri)                                          // ✅ 按引用传递（整个 RepeatItem）
this.buildItem3(ri.item)                                     // ❌ 反例。按值传递，不刷新
```

## 八、Repeat / 循环渲染与长列表

来源：`arkts-new-rendering-control-repeat`（1583 行）、`arkts-v1-v2-migration-rendering-control-repeat`（1769 行）。

### 8.1 为什么 V2 推荐 Repeat

`arkts-new-rendering-control-repeat`"概述"原文：

> "Repeat 与 LazyForEach 组件的区别：
> - Repeat **直接监听状态变量的变化**，而 LazyForEach 需要开发者实现 IDataSource 接口，手动管理子组件内容/索引的修改。
> - Repeat 还增强了**节点复用能力**，提高了长列表滑动和数据更新的渲染性能。
> - Repeat 增加了**渲染模板（template）**的能力，在同一个数组中，根据开发者自定义的模板类型（template type）渲染不同的子组件。
> 相较于 LazyForEach，Repeat 用法更加简单，渲染性能更好，**建议开发者优先使用 Repeat**。"

`arkts-v1-v2-migration-rendering-control-repeat` 原文："**状态管理 V2 推荐使用 Repeat 替代 ForEach。**…Repeat 需要和状态管理 V2 一起使用。"

迁移对照（同文档）：`ForEach → Repeat`；`LazyForEach → Repeat`。

### 8.2 使用限制（原文，逐条，全部可执行）

- "Repeat **必须在滚动类容器组件内使用**，仅有 **List、ListItemGroup、Grid、Swiper 以及 WaterFlow** 组件支持 Repeat 懒加载场景。"
- "循环渲染只允许创建一个子组件…例如：Repeat 与 List 组件配合使用时，子组件需要为 ListItem 组件或者 ListItemGroup 组件。"
- **"Repeat 懒加载模式不支持与状态管理（V1）配合使用，否则会导致渲染异常。"**
- "滚动容器组件内只能包含一个 Repeat。以 List 为例，**不建议同时包含 ListItem、ForEach、LazyForEach，不建议同时包含多个 Repeat**。"
- "当 Repeat 与自定义组件或 @Builder 函数混用时，**必须将 RepeatItem 类型整体进行传参**，组件才能监听到数据变化。"
- "Repeat 子组件复用时**不会触发 aboutToRecycle、aboutToReuse 生命周期**。"
- "Repeat 功能依赖数组属性的动态修改。如果数组对象被**密封（sealed）或冻结（frozen）**，将导致 Repeat 部分功能失效…"（常见触发：`makeObserved` 转换某些实现会自动密封；显式 `Object.seal()/Object.freeze()`）

### 8.3 `each` / `template` / `key` / `virtualScroll` 用法

**基础写法（单一类型子组件）**：
```
List() {
  Repeat<string>(this.dataArr)
    .each((ri: RepeatItem<string>) => {
      ListItem() { Text('each_' + ri.item).fontSize(30) }
    })
    .virtualScroll({ totalCount: this.dataArr.length })  // 打开懒加载，totalCount 为期望加载的数据长度
}
.cachedCount(2)
```

**多模板**：`.template()`（需在懒加载模式下使用）、`.templateId()`；"`.each()` 等价于 template type 为空字符串的 `.template()`"；"当多个 template type 相同时（包括空字符串），Repeat 仅生效最新定义的 `.each()` 或 `.template()`"；"**只有相同 template type 的节点可以互相复用**"。

**键值生成规则（`arkts-new-rendering-control-repeat`"键值生成规则"节，逐字）**：
- "当 `.key()` 缺省时，Repeat 会生成**新的随机键值**。当发现有重复 key 时，Repeat 会在已有键值的基础上递归生成新的键值，直到没有重复键值。"
- "**键值（key）与索引（index）的区别**：键值是数据项的唯一标识符，Repeat 根据键值是否发生变化判断数据项是否更新；索引只标识数据项在数组中的位置。"
- 使用限制：① "即使数组发生变化，开发者也**必须保证键值 key 唯一**"；② "每次执行 `.key()` 函数时，使用相同的数据项作为输入，输出必须是一致的"；③ "**允许在 .key() 中使用 index，但不建议开发者这样做**。因为在数据项移动时索引 index 发生变化的同时 key 值也会改变，导致 Repeat 认为数据发生变化，从而触发子组件重新渲染，降低性能表现"；④ "**推荐将简单类型数组转换为类对象数组，并添加一个 readonly id 属性，在构造函数中初始化唯一值。**"

**两种加载模式对照**

| | 懒加载模式（`.virtualScroll()`） | 全量加载模式（省略 `.virtualScroll()`） |
| --- | --- | --- |
| 容器约束 | 必须与 List / ListItemGroup / Grid / Swiper / WaterFlow 配合 | 不受滚动容器限制，可在任意场景使用 |
| 状态管理 | 需要和状态管理（V2）配合 | **支持与状态管理（V1）配合** |
| 模板特性 | 支持 template | **渲染模板特性（template）不可用** |
| 刷新触发 | 键值变化或数据变化均会触发刷新 | **页面刷新取决于键值变化：如果更新前后键值相同，即使数据改变，页面也不会刷新** |
| 长列表建议 | "对于长列表场景，懒加载模式支持按需加载子组件，**建议开发者优先使用懒加载模式**" | "对于长数据列表（**数据长度大于 30**），如果关闭懒加载，Repeat 会一次性加载全量子组件，此操作耗时长，**不建议使用**" |

- 节点复用默认开启；"从 API version 18 开始，在懒加载模式下，可以通过配置 `reusable` 字段选择是否启用复用功能。为了提高渲染性能，**建议开发者保持节点复用**。"

### 8.4 `ForEach` 的已知刷新问题（官方 FAQ）

`faqs-arkui-619`（"ForEach 循环渲染中组件 UI 刷新异常问题"）两个现象：
- **问题一**："当 ForEach 组件进行的是**非初次渲染**，会出现数据更改但 UI 不刷新现象"——数组整体赋新值但**键值（label）未变**时不刷新；键值变了才刷新。
- **问题二**："当数组数据被删除时，出现**重复显示**问题"。
- `faqs-arkui-41`（"使用 ForEach&LazyForEach 循环渲染时，会出现更改数据源时，界面不刷新的情况。如何解决"）——同名条目存在（正文极短，指向 ForEach 键值生成规则）。

> **对 Weaver 的直接含义**：`ForEach` 的 key 函数若只用 `index` 或用会变的字段，就会出现"删除后重复显示""改了数据不刷新"这两类症状；`Repeat` 通过 `readonly id` + `.key(item => item.id)` 把这个问题制度化解决。

## 九、V1/V2 混用规则（API 19+）

来源：`arkts-v1-v2-mixusage`（API 19 及之后）、`arkts-v1-v2-mixusage-before-api-version`（API 19 之前）。

### 9.1 API 19 及之后的"限制条件"（逐字 3 条）

1. **"V1 装饰器不能和 @ObservedV2 一起使用。"** 原因（原文）："因为 @ObservedV2/@Trace 有自己独立的观察能力，不仅可以在 @ComponentV2 中使用，也可以独立在 @Component 中使用，状态管理框架不希望其观察能力和 V1 的观察能力混合使用，所以依旧维持禁止现状。"
2. **"V2->V1，V1 不支持用装饰器接收 @ObservedV2 装饰的 class，否则编译报错。"** ← **这正是我们踩过的坑**（V1 组件用装饰器接收 `@ObservedV2` 的 class → 编译报错）。**在 API 19+ 依旧禁止**，这是三条"不改的禁令"之一。
3. "V1 中 @Link 遵循其原本初始化规则，**只能被 V1 状态变量初始化**…因为 V1 中 @Link 仅能和 V1 状态变量建立双向同步关系，而 V2 中如果想实现双向同步，可以使用 @Param、@Event。"

### 9.2 新增两个接口

**`UIUtils.makeV1Observed`** — "将不可观察的对象包装成状态管理 V1 可观察的对象，**能力等同于 @Observed，其返回值可初始化 @ObjectLink**。"（API 19+）
- 主要和 `enableV2Compatibility` 搭配实现 **V2→V1** 的传递；
- "可将普通 class、Array、Map、Set、Date 类型转换为 V1 的状态变量"；
- "如果 makeV1Observed 接受的数据已经是 V1 的状态变量，则返回自身，不做任何改变"；
- **"makeV1Observed 不会递归执行，仅会将第一层包装成 V1 的状态变量。"**
- 限制："不支持 collections 类型和 @Sendable 装饰的 class"；"不支持非 object 类型"；"不支持 undefined、null"；"不支持 @ObservedV2、makeObserved 的返回值和 V2 装饰器装饰的 built-in 类型的变量（Array、Map、Set 和 Date）"。

**`UIUtils.enableV2Compatibility`** — "将 V1 的状态变量使能 V2 的观察能力，即让 V1 状态变量可以在 @ComponentV2 中观察到变化。"（API 19+）
- 应用于 **V1→V2**：V1 状态变量调用后传到 `@ComponentV2` 即可在 V2 中观察到变化；
- "只能作用于 V1 的状态变量。V1 状态变量为 V1 装饰器装饰的变量，即 @Observed 装饰的变量，或 @State、@Prop、@Link、@Provide、@Consume 和 @ObjectLink（@ObjectLink 需是 @Observed 装饰的实例或者 makeV1Observed 的返回值）装饰的变量。否则，将返回入参自身。"
- **"enableV2Compatibility 会递归遍历 class 的所有属性，Array/Set/Map 的所有子项，直到遇到非 V1 状态变量的数据，则停止当前分支的遍历。"**
- 限制与 makeV1Observed 相同（4 条）。

### 9.3 混用规则（逐字，含官方"建议/不建议"）

- **V1→V2 传递复杂类型数据，需要调用 `enableV2Compatibility`**，否则无法实现数据联动；"**建议在 V2 组件的构造处调用**，否则当变量被整体赋值时，需要再次手动调用 enableV2Compatibility"。
  ```
  // 建议用法
  SubComponentV2({param: UIUtils.enableV2Compatibility(this.state)})
  ```
- **V2→V1 传递复杂类型数据**，"在 V2 中优先声明成 V1 的状态变量数据，并调用 UIUtils.enableV2Compatibility"：
  ```
  @Local unObservedClass: UnObservedClass = UIUtils.enableV2Compatibility(UIUtils.makeV1Observed(new UnObservedClass()));
  @Local observedClass: ObservedClass = UIUtils.enableV2Compatibility(new ObservedClass());
  ```
- `enableV2Compatibility(makeV1Observed())` **不会改变双方本身的观察能力**：
  - "在 V1 中…等于 V1 的观察能力，观察数据本身的赋值和第一层属性的赋值，无法深度观察，如果需要深度观察，则需要配合 @ObjectLink。"
  - "在 V2 中…可以深度观察，但是**需要每一层都是 @Observed 装饰的 class，或者是 makeV1Observed 的返回值**。"
  - **"不使用 enableV2Compatibility 和 makeV1Observed 会导致双重代理问题，使同一状态对象被 V1 和 V2 两套状态管理体系同时生成代理对象，从而引起监听逻辑冲突。"**
- 新增数据要用 `makeV1Observed` 包：
  ```
  let arr: Array<ArrayItem> = UIUtils.enableV2Compatibility(UIUtils.makeV1Observed(new Array<ArrayItem>()));
  arr.push(new ArrayItem());                      // 新增数据不是 V1 状态变量，所以不会具有 V2 观察能力
  arr.push(UIUtils.makeV1Observed(new ArrayItem())); // 新增数据是 V1 的状态变量，默认在 V2 中可观察
  ```
- built-in 类型（Array/Map/Set/Date）："虽然开发者在不调用 UIUtils.enableV2Compatibility 时，也可以在一些简单场景下实现数据刷新，但是会带来**双重代理导致性能较差**的问题，所以**建议**开发者使用 `UIUtils.enableV2Compatibility(UIUtils.makeV1Observed())`。"
- `@Track` 差异："对于有 @Track 装饰属性的类，**非 @Track 装饰的属性在 @ComponentV2 中使用不会崩溃，在 @Component 中使用仍会崩溃**。"

### 9.4 API 19 之前（对照，说明"放宽了什么"）

`arkts-v1-v2-mixusage-before-api-version`"限制条件"逐字：
- "V1 和 V2 的装饰器不允许混用…编译会报错。"
- "V1 装饰器不能和 @ObservedV2 一起使用，否则编译报错。"
- "V2 装饰器不能和 @Observed 一起使用，否则编译报错。"
- **"V1->V2 传递状态变量只支持简单类型，不允许传复杂类型的状态变量。比如传递 @Observed 装饰的 class、装饰器修饰的 built-in 类型（Array、Map、Set、Date），编译报错。"**
- "V2->V1 可以传简单类型状态变量和普通 class。如果传递 @ObservedV2 装饰的 class、装饰器修饰的 built-in 类型（Array、Map、Set、Date），编译报错。"
- "V1 中 @ObjectLink 只接受 @Observed 装饰的 class 初始化。"
- "多个装饰器不允许装饰同一个变量（@Watch、@Once、@Require 除外）。"

该文档"混用场景总结"（逐字）：
> "当 V1 中混用 V2 自定义组件时（即 V1 的组件或者类数据向 V2 传递），**大部分 V1 的能力在 V2 都是被禁止的**。当 V2 中混用 V1 自定义组件时（即 V2 的组件或者类数据向 V1 传递），做了部分功能开放。例如：@ObservedV2 和 @Trace，这也是对 V1 嵌套类数据的观测能提供的最大的帮助。所以**在代码开发过程中，不建议开发者混用 V1 和 V2 版本**。然而，在代码迁移方面，V1 的开发者可以逐步将代码迁移到 V2…同时，**不建议在 V2 的代码架构中混用 V1 的代码**。"

**一句话总结（对 Weaver）**：V1/V2 混用的正确姿势是"**不要混**"；必须混时，用 `enableV2Compatibility` / `makeV1Observed` 拉齐观察能力，否则会双重代理。我们项目已经是纯 V2（`@ComponentV2` + `@Local`），这是最优解，**不要为了兼容个别 V1 组件而引入混用**。

## 十、@ObservedV2/@Trace 的观测边界与官方承认的限制

来源：`arkts-new-observedv2-and-trace`（1203 行）、`arkts-v1-v2-update-difference`。

### 10.1 观测边界（能观测什么）

**装饰器说明（逐字）**：
- `@ObservedV2`：装饰 class；"需要放在 class 的定义前，使用 new 创建类对象"。
- `@Trace`：可装饰"class 中成员属性。属性的类型可以为 **number、string、boolean、class、Array、Date、Map、Set 等类型**。**@Trace 不支持观察 Function 类型的数据，修改 @Trace 装饰的 Function 类型的数据，UI 不会刷新。**"

**内置类型的可观测 API（官方表格，逐字，这就是"数组的哪些操作会被观测"的答案）**：

| 类型 | 可观测变化的 API |
| --- | --- |
| **Array** | `push`、`pop`、`shift`、`unshift`、`splice`、`copyWithin`、`fill`、`reverse`、`sort` |
| Date | `setFullYear`、`setMonth`、`setDate`、`setHours`、`setMinutes`、`setSeconds`、`setMilliseconds`、`setTime`、及对应 UTC 系列 |
| Map | `set`、`clear`、`delete` |
| Set | `add`、`clear`、`delete` |

**注意边界**：列表里**没有 `concat`、`map`、`filter`、`slice`、`indexOf`、`flat`**——这些不改变原数组的方法本来也不需要刷新；但**用它们的结果整体赋值给 `@Trace` 属性是会被观测的**（因为那是属性赋值）。而"数组元素属性"的观测要求元素类本身是 `@ObservedV2` + 该属性 `@Trace`（见 10.2 的嵌套场景）。

**官方对照实验（`arkts-v1-v2-update-difference`，逐字）**：
```
this.obsObjA = new ObsObjA('obsObjA++');   // V1/V2 都触发刷新
this.arr = [new ObsObjC('propC1'), ...];   // V1/V2 都触发刷新
this.arr[0] = new ObsObjC('propC3');       // V1/V2 都触发刷新
this.obsObjA.propA = 'propA3';             // V2 需 @Trace；V1 需 @Track（或未 @Track 时也能观测）
this.obsObjA.obsObjB.propB = 'propB3';     // "对于 V1，只能观察一层的变化…第 4 行 Text 不更新；对于 V2，只要被 @Trace 装饰，第 4 行的 Text 就能更新"
this.arr[0].propC = 'propC4';              // "对于 V1…数组项的属性赋值是第二层的修改，第 7 行的 Text 不会更新；对于 V2…会更新"
```

**结论（回答"什么时候必须换新对象"）**：
- 需要 UI 刷新时，**数组/对象的整体赋值（换新对象）永远有效**（V1/V2 都是）；
- **V2 下不需要**为了刷新而换新对象——只要改的是被 `@Trace` 装饰的属性，或者调用的是上表中的 Array/Map/Set/Date API，就会刷新；
- **V1 下需要**：深层属性变化（第二层及以下）V1 观测不到，只能靠换新对象或逐层 `@ObjectLink` 拆解；
- **注意"已存在元素的属性"**：`this.arr[0].propC = ...` 要求 `ObsObjC` 被 `@ObservedV2` 且 `propC` 被 `@Trace`，否则不刷新。

### 10.2 官方承认的限制（逐条，全部来自 `arkts-new-observedv2-and-trace`"使用限制"）

1. "非 @Trace 装饰的成员属性用在 UI 上**无法触发 UI 刷新**。"
2. "**@ObservedV2 仅能装饰 class，无法装饰自定义组件**。"（`@ObservedV2 struct Index {}` 编译报错）
3. "**@Trace 不能用在没有被 @ObservedV2 装饰的 class 上**。"
4. "**@Trace 是 class 中属性的装饰器，不能用在 struct 中**。"（`@ComponentV2 struct Comp { @Trace message: string }` 编译报错）
5. "**@ObservedV2、@Trace 不能与 @Observed、@Track 混合使用**。"（都编译报错）
6. "**使用 @ObservedV2 与 @Trace 装饰的类不能和 @State 等 V1 的装饰器混合使用，编译时报错。**"
7. "**继承自 @ObservedV2 的类无法和 @State 等 V1 的装饰器混用，运行时报错。**"（注意是**运行时**，不是编译时，更隐蔽）
8. "**使用 @ObservedV2 与 @Trace 装饰器的类，需通过 `new` 操作符实例化后，才具备被观测变化的能力。**"
9. "**@ObservedV2 的类实例无法直接使用 `JSON.parse` 反序列化获得**（直接使用 JSON.parse 反序列化获得的对象无法观察属性变化），可搭配三方库 class-transformer 实现反序列化后可观察。"
10. （`arkts-new-observedv2-and-trace` 专节）"**router 传递的 @ObservedV2 类型显示异常**"："由于经过序列化生成的属性名称与类中的原始属性名称不一致，**不能直接通过 as 类型转换成 @ObservedV2 的实例，需要反序列化重新生成 @ObservedV2 实例。**"

> 第 9、10 条对 Weaver 极其重要：**任何经过 JSON 序列化的路径（持久化落库、备份导出导入、跨页面/跨 ability 传参）拿回来的对象都不是可观测的 `@ObservedV2` 实例**，必须重新构造成类实例（或走 class-transformer / `makeObserved`），否则改了属性 UI 不刷新。我们项目有 `database/`、`repository/`、`store/BackupTypes.ets`、`ImportService.ets`，是这条限制的高危区。

### 10.3 相关 V2 装饰器的官方限制（回答第 15 问的其余部分）

**`@Param`（`arkts-new-param`"限制条件"）**
- "只能在 @ComponentV2 装饰器的自定义组件中使用"（在 `@Component` 里编译报错）；
- "**需要初始化**。支持使用本地初始值或外部传入值进行初始化。当存在外部传入值时，优先使用外部传入值。**不允许既不使用本地初始值，也不使用外部传入值**。"（要"必传"用 `@Require @Param`）
- **"使用 @Param 装饰的变量在子组件中无法被直接修改。但是，如果装饰的变量是对象类型，在子组件中可以修改对象的属性。"** 官方反例注释："错误用法，不允许在子组件中更改 @Param 变量，**编译时会报错**"；正例注释："允许在子组件中更改对象中属性，该修改会同步到父组件数据源上，当属性被 @Trace 装饰时，可观测到对应 UI 刷新"。
- 设计动机（原文）："装饰器的不同限制使得父子组件之间的传值规则复杂、不易使用。因此推出 @Param 装饰器，表示组件从外部传入的状态。"

**`@Event`（`arkts-new-event`）**
- "为了实现子组件向父组件要求更新 @Param 装饰变量的能力…"；"由于 @Param 装饰的变量在本地无法更改，使用 @Event 装饰器装饰回调方法并调用，可以实现更新数据源的变量，再通过 @Local 的同步机制，将修改同步回 @Param 装饰的变量。"
- 语义："**@Event 装饰非回调类型的变量不会生效。当 @Event 没有初始化时，会自动生成一个空的函数作为默认回调。**"；"当 @Event 未被外部初始化，但本地有默认值时，会使用本地默认的函数进行处理。"
- 允许装饰类型："回调方法，例如 `()=>void`、`(x:number)=>boolean` 等"；允许传入的函数类型："**箭头函数**"。
- 限制："**@Event 只能用在 @ComponentV2 装饰的自定义组件中。当装饰非方法类型的变量时，不会有任何作用。**"（在 `@Component` 里编译报错）

**`@Computed`（`arkts-new-computed`"使用限制"）**
- "**@Computed 为方法装饰器，仅能装饰 getter 方法。**"（`@Computed val: number = 0` / `@Computed func(){}` 都编译报错）
- **纯度要求（原文）**："不建议开发者在 @Computed 装饰的 getter 方法中做**除获取数据外其余的逻辑操作**"；"**在 @Computed 装饰的 getter 方法中，不能改变参与计算的属性，以防止重复执行计算属性导致的 appfreeze。**" 官方给了循环计算导致 appfreeze 的完整反例。
- 开销提示："对于简单计算，**不建议使用计算属性**，因为计算属性本身也有开销。对于复杂的计算，@Computed 能带来性能收益。"
- 行为："@Computed 会检测被计算的属性变化，当被计算的属性变化时，@Computed **只会被求解一次**。"
- 能力："@Computed 装饰的属性可以被 @Monitor 监听变化"；"@Computed 装饰的属性可以初始化 @Param"。

**`@Monitor`（`arkts-new-monitor`"概述"）**
- "**@Monitor 装饰器支持在 @ComponentV2 装饰的自定义组件中使用，未被状态变量装饰器 @Local、@Param、@Provider、@Consumer、@Computed 装饰的变量无法被 @Monitor 监听到变化。**" ← **"@Monitor 只能监听 V2 变量"的准确表述**。
- "支持在类中与 @ObservedV2、@Trace 配合使用，**不允许在未被 @ObservedV2 装饰的类中使用 @Monitor 装饰器。未被 @Trace 装饰的属性无法被 @Monitor 监听到变化。**"
- 比较语义："判断属性是否变化使用的是**严格相等（===）**…当在一次事件中多次改变同一个属性时，将会使用初始值和最终值进行比较以判断是否变化。"（与 `@Watch` 的"每次都回调"形成对比）
- **"当 @Monitor 监听整个数组时，更改数组的某一项不会被监听到。无法监听内置类型（Array、Map、Date、Set）的 API 调用引起的变化。"** ← 这是一条**明确的能力缺口**（与 `@Trace` 的 Array API 表互补：`@Trace` 管刷新，`@Monitor` 管回调，后者覆盖不到 API 调用）。
- 执行时机（`arkts-v1-v2-update-difference`，逐字）："**V2 装饰变量赋值，对象属性或数组（Map、Set）项变化，会触发 @Monitor 的异步执行。如果状态变量被修改多次，则 @Monitor 函数只会执行一次。**"（对应 `@Watch`："**会触发 @Watch 的同步执行。如果状态变量被修改多次，则 @Watch 函数会同步执行多次。**"）
- "从 API 版本 26.0.0 开始，支持配置 `MonitorDecoratorOptions`…支持在监听路径中设置通配符 '*'"，且"**对 @Monitor 部分能力进行修正**，详情见 @Monitor 使用配置项前后的对比"。
- 另有 `@SyncMonitor`（同步监听）作为补充（`arkts-decorator-overview`）。

**`@Provider`/`@Consumer` 必须本地初始化（`arkts-new-provider-and-consumer`，逐字）**
- 概览表："`@Consume(r)` — **必须本地初始化**，当找不到 @Provider 时使用本地默认值。"（并注明："API version 20 以前，@Consume **禁止本地初始化**，当找不到对应 @Provide 的时候，会抛出异常；从 API version 20 开始，@Consume 支持设置默认值，如果没有设置默认值，且找不到对应 @Provide 时，会抛出异常。"）
- 变量传递表："从父组件初始化 — **@Provider 和 @Consumer 装饰的变量仅允许本地初始化，不允许从外部传入初始化。**"
- "3. **@Provider 和 @Consumer 只支持本地初始化，不支持外部传入初始化。**"
- 注意版本差异：**"必须本地初始化"是 V2（`@Provider`/`@Consumer`）的规则**；对应的 V1（`@Provide`/`@Consume`）是"@Consume 禁止本地初始化（API 20 前）"。两者容易记反——**我们踩的坑是 V2 侧的"必须本地初始化"，与官方一致。**

### 11.2 核心问题：把 Navigation 移除、改用外壳内状态切换，是否违背官方推荐？

**结论：属于"偏离官方推荐路径"，但不属于"违反官方规定"；且我们踩的两个坑都是用法错误，不是 Navigation 的固有缺陷。当前做法的真实代价是"返回键/手势必须自己实现"，而这一块我们还没实现。**

分三层说清：

**(1) 官方说了什么、没说什么**

- **说了**（`arkts-navigation-introduction`）："推荐使用组件导航（Navigation）来实现页面跳转以及组件内的跳转，以获得更佳的使用体验。"——这是**推荐性**表述，语气是"推荐/更佳体验"，不是"必须"。
- **说了**（`js-apis-router` / `arkts-routing`）：router 是"（不推荐）"。
- **没说的**：文档中**未找到**任何"应用必须使用 Navigation"、"禁止用状态变量切换视图"的条文；也**未找到**"用状态切换代替路由"的官方示例或最佳实践。

→ 所以：**没有"违规"，只有"没走推荐路径"**。真正需要向用户交代的风险不是"合不合规"，而是"少拿了什么"。

**(2) 我们踩的坑，官方都有明确答案——说明当初不是 Navigation 的错**

| 我们的症状 | 官方原文 | 正确写法 |
| --- | --- | --- |
| `hideNavBar(true)` + 空路由栈 → 整屏空白 | `faqs-arkui-1018`："设置为 true 时，隐藏 Navigation 的导航页，**包括标题栏、内容区和工具栏**…反之显示空白。" | 主界面必须放在 **Navigation 的子节点（即 NavBar 内容区）**；`hideNavBar` 保持 false；仅当"要把某个子页当主页"时才用 `hideNavBar(true)` + push 子页 + `setInterception`（`faqs-arkui-1018`/`faqs-arkui-1094` 方案一） |
| `NavigationMode` 默认 Auto 在平板走分栏，和自绘外壳打架 | `ts-basic-components-navigation`："默认值：NavigationMode.Auto"；`faqs-arkui-1276`："当为折叠屏或平板时，默认分栏显示" | **显式 `.mode(断点 ? Stack : Split)`**，别吃默认值。官方最佳实践就是这么写的（`bpta-multi-device-page-layout`：`.mode(this.mainWindowInfo.widthBp === WidthBreakpoint.WIDTH_SM ? NavigationMode.Stack : NavigationMode.Split)`） |
| `pop` 回到导航页而不退出页面 | `faqs-arkui-430`："pop 时均会返回到导航栏 NavBar…系统会优先显示 Navigation 组件自带的导航栏" | `hideNavBar(true)`，或在 `onBackPressed` 里 `router.back()`；`arkts-navigation-jump`："**无法直接操作 NavBar 导航栏，若想跳转到 NavBar 页面只能通过 clear 清空路由栈的方式**" |

**一句话**：我们的两个"坑"（白屏、Auto 分栏）如果按官方写法本来都不会发生。它们是**集成方式错误**，被误判成了"Navigation 不适合我们"。

**(3) 官方对"三栏工作台"到底推荐什么？——有明确表态，而且正好是我们的形态**

`bpta-multi-device-page-layout`（最佳实践"页面布局场景"）：

- 分栏布局三大类："常见的分栏布局包括**侧边栏、单/双栏和三分栏**。"
- **侧边栏** → `SideBarContainer`；官方还给了与 Navigation 的分工判断（逐字）：**"单/双栏与侧边栏的主要区别是单/双栏的导航栏能够控制内容区的路由跳转，例如商品列表与商品详情；侧边栏通常不控制内容区展示的内容，例如图文详情与评论区。"**
- **单/双栏** → `Navigation` 的 `mode`。并给了"二分栏典型场景——聊天"的路由→全屏切换写法（`isNavFullScreen` 决定 Split/Stack），**这正是"二级页面全屏覆盖"的官方版本**：
  ```
  getNavMode(): NavigationMode {
    if (!this.isNavFullScreen && this.mainWindowInfo.widthBp !== WidthBreakpoint.WIDTH_SM) {
      return NavigationMode.Split;
    }
    return NavigationMode.Stack
  }
  ```
- **三分栏** → 原文："三分栏基于横向断点，动态控制导航栏的显示模式和侧边栏是否显示，实现三分栏布局。**实现方案：在不同横向断点下，动态控制 SideBarContainer 组件的 showSideBar、sideBarWidth 属性，和 Navigation 组件的 mode、navBarWidth 属性实现目标效果。**"
  ```
  SideBarContainer(断点决定 Overlay/Embed) {           // ← 第一栏（侧栏）
    侧栏内容
    Column() {
      Navigation(this.pathStack) {                     // ← 第二 + 第三栏
        NavigationBarView({ /* 列表 */ })
      }
      .mode(widthBp === WIDTH_SM ? NavigationMode.Stack : NavigationMode.Split)
      .navBarWidth(widthBp === WIDTH_MD ? '50%' : '40%')
      .navDestination(this.PageMap)                    // ← 主内容
    }
  }
  .showSideBar(this.isShowingSidebar)
  .sideBarWidth(new WidthBreakpointType('80%', '50%', '20%', '20%').getValue(this.mainWindowInfo.widthBp))
  ```
- "三分栏典型场景——邮箱"进一步给了**单栏时的优先级处理**："根据内容的重要性，开发者在单栏模式下显示邮件详情，在双栏模式下显示收件箱和邮件详情，在三栏模式下显示账户信息、收件箱和邮件详情。"
- "三分栏典型场景——日历"给了**反向优先级**的处理（单栏优先显示 Navigation 导航栏）：通过 `onNavigationModeChange` 在单栏时 `pathStack.clear()`、双栏时 `pushPath` 重新填内容区。
- 商务办公最佳实践（`multi-business-office`）的核心功能列表里，前两条就是：**"侧边栏显隐：监听断点变化，设置 SideBarContainer 组件的 SideBarContainerType 属性或改变 showSideBar 属性参数…"** 与 **"分栏布局：分栏布局通过 Navigation 实现，监听断点变化，根据不同断点或状态改变 Navigation 的 mode 属性，实现单双栏切换的效果。"**

→ **官方对"侧栏 + 列表 + 主内容"的态度非常明确：`SideBarContainer` 管最左栏，`Navigation` 管剩下两栏，`mode`/`navBarWidth` 由断点显式驱动。** 我们的自绘三栏外壳，等于**同时替掉了这两者**。这不是错，但是"另起炉灶"。

### 11.3 建议（按代价从小到大，逐条给理由与风险）

#### 建议 A（**立刻做，成本极低，收益最高**）：补上返回键/侧滑处理

- **现状**：`Index.ets` 无 `onBackPress`；`AppShell` 无 `onBackPressed`。二级覆盖页（设置/人物/世界观/灵感）打开时，按系统返回键或侧滑 → **直接退出应用**，而不是关闭覆盖页。
- **建议做法**：在 `@Entry struct Index` 上实现 `onBackPress(): boolean`，把"当前是否有覆盖页"暴露给页面层（例如 `AppShell` 通过 `@Link`/`@Provider`/回调上报，或把 `route !== SHELL` 的判断提升到 Index）。
  ```
  // @Entry 页面（伪代码，示意形态）
  onBackPress(): boolean {
    if (shellRef.isOverlayOpen()) { shellRef.closeTopOverlay(); return true; }  // 自己处理，不走路由
    return false;                                                              // 交回系统（退出/后台）
  }
  ```
- **理由**：`faqs-arkui-531` 明确 `onBackPress` 是"当用户点击返回按钮或**侧滑返回**时触发，仅 @Entry 装饰的自定义组件生效"；返回 `true` 表示"页面自己处理返回逻辑，不进行页面路由"。**这是无 Navigation 方案下唯一能接住返回事件的位置。**
- **风险/注意**：`faqs-arkui-531` 专门警告了误拦截导致"侧滑无法从首页退出应用"，并给出排查日志关键字（`router user onBackPress return true`、`router consumed backpressed event`、`禁止手势返回`）。所以**必须保证"无覆盖页时返回 false"**，并在真机上验证首页可正常滑动退出。另外 `faqs-arkui-1146`（"window 弹窗打开时 onBackPress 失效"）提示：若有自定义弹窗打开，返回键的优先级需要额外验证。

#### 建议 B（**中期，若要做平板/PC 双栏**）：按官方三分栏模式重构

- **现状**：自绘外壳自己算三栏；断点用 `mediaquery` 手写。
- **建议**：若后续要在平板/PC 上做"侧栏 + 列表 + 主内容"的官方式分栏（可拖拽分割线、单栏/双栏/三栏按断点切换、`splitPlaceholder` 占位页、转场动画），就把最左栏交给 `SideBarContainer`、把"列表 + 主内容"交给 `Navigation(Split)`：
  - `.mode(断点 ? NavigationMode.Stack : NavigationMode.Split)`（**不要用 Auto**）；
  - `.navBarWidth(...)` + `.navBarWidthRange([...])` + `.minContentWidth(...)`；
  - 列表 → Navigation 子节点（NavBar 内容区）；主内容 → `NavDestination`；
  - 二级页继续用 `navDestination` 的 PageMap 或系统路由表。
- **理由**：这是 `bpta-multi-device-page-layout` 与 `multi-business-office` 的官方做法，能白拿：可拖拽分割线、`enableModeChangeAnimation`、`geometryTransition` 共享元素动画、`systemBarStyle`/`preferredOrientation` 沉浸式页面、`UIObserver.on('navDestinationUpdate')` 埋点、`onActive`/`onInactive` 生命周期（`ts-basic-components-navdestination`）。
- **风险**：① 需要重排 `AppShell` 的布局层级，工作量大；② 需要重新验证 V2 状态在 NavDestination 之间的传递（若用 `@Provider/@Consumer` 跨页共享 store，注意"必须本地初始化"这条限制，以及"V1 组件不能接收 `@ObservedV2` class"这条禁令——只要全项目保持纯 V2 就不触发）；③ `aboutToAppear` 里做栈操作会白屏（官方警告），要放对时机。

#### 建议 C（**保持现状也可以用，但要把"文档缺失的补偿"补齐**）

如果决定长期不用 Navigation，那么必须由我们自己实现 Navigation 免费给的那些能力，至少包括：

| Navigation 免费给的能力 | 我们需要自己实现的替代 | 当前状态 |
| --- | --- | --- |
| 返回键/侧滑返回 | `@Entry.onBackPress` | **缺失（建议 A）** |
| 页面生命周期 `onShown/onHidden/onWillShow/onWillHide/onActive/onInactive` | 在路由切换函数里手动挂钩子 | 未确认 |
| 转场动画 / 共享元素（`geometryTransition`） | 自绘 `animateTo`/属性动画 | 未确认 |
| 沉浸式页面（`enableStatusBar`/`enableNavigationIndicator`/`preferredOrientation`） | `window` 接口手动管理 | 未确认 |
| 路由栈查询与埋点（`getPathStack`、`UIObserver`） | 自维护 `route`/`routeBack`（我们已有雏形） | 部分具备 |
| `splitPlaceholder` 分栏占位 | 自绘（因为不做分栏，不需要） | N/A |
| 跨页面参数传递 | 我们已有 `routeParam: string` | **只传一个字符串**，扩展性弱（官方 `param` 是 `unknown`，可传任意对象） |

> **对 `routeParam: string` 的一点提示**：官方 `pushPath` 的 `param` 类型是 `unknown`，"可以是用户自定义的类型"（`ts-basic-components-navigation`）。我们用单个 string 承载二级页入参，后续若要传复合参数会很快不够用；建议至少改成 `@Local routeParams: object | undefined`（与 Navigation 的能力对齐，将来迁移也少改一层）。

#### 建议 D（独立的、与导航无关，但同样是"官方踩坑"）：序列化边界上的 V2 可观测性

- `arkts-new-observedv2-and-trace` 明确两条：**`JSON.parse` 得到对象不可观测**；**router 传过来的 `@ObservedV2` 实例也不能直接 `as`**。
- 我们的 `database/`、`repository/`、`ImportService.ets`、`store/BackupTypes.ets` 都在做序列化往返。**从库里/备份文件里读回来的对象，必须重新 `new` 成类实例（并保证 `@Trace` 属性被赋值），否则改了属性 UI 不会刷新。**
- 若某处确实需要"非观察数据变可观察"，官方给了 `makeObserved`（`arkts-new-makeobserved`）与 `canBeObserved`（`arkts-new-canbeobserved`）——文档已确认这两个接口存在，本次未逐字精读其限制（超出本报告范围）。

### 11.4 "移除 Navigation 是否可接受"——一句话答复

> **可以接受，但必须知道它是"自选方案"而不是"官方方案"，并且必须自己补上官方免费提供的能力。**
> 具体到今天就有一个必须补的：**`@Entry` 的 `onBackPress`**（否则二级覆盖页按返回键会退出应用）。如果将来要做平板/PC 的官方式三栏分栏（可拖拽分割线、分栏占位页、页面转场、沉浸式），那"移除 Navigation"的代价会显著上升，届时按 §11.3 建议 B 迁回 `SideBarContainer + Navigation(Split)` 更划算。
